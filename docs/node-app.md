# Endpoint app (`src/node`) details

Summary in [CLAUDE.md](../CLAUDE.md).

- **Implementation (`src/node`, own pnpm project)**: Expo SDK 58, Expo Router (`src/app/`), `expo-dev-client`. **Fluent UI React v9 is DOM-only and cannot run in React Native**, so the app reuses only the platform-agnostic design tokens from `@fluentui/tokens` (`teamsLightTheme`/`teamsDarkTheme`, same as the web app) and has its own thin components in `src/components/` (`Text`, `Button`, `Card`, `Screen`, `ChoiceGroup`, and `Logo`/`Brand`: the web app's `logo.svg` redrawn with `react-native-svg` plus the lowercase two-colour Inter wordmark, `#14b8d4` split / `#4f5df0` cortex, used as the Home header title; keep in sync with the web sidebar) that read tokens through `useTheme()` (`src/theme/ThemeContext.tsx`; preference System/Light/Dark, default System, persisted in AsyncStorage). Do not add `@fluentui-react-native` or another component library. Inter is bundled (`@expo-google-fonts/inter`, no CDN; RN has no variable fonts, so weights map to families in `theme/fonts.ts`). i18n: i18next with bundled JSON (`src/i18n/locales`, en + ro; stored choice, then device language, fallback en). Same conventions as the web app: cards, hairline borders, no shadows, TypeScript strict, no `any`. Tests: **Jest** (`jest-expo` preset, `@testing-library/react-native` 14 where `render`/`renderHook`/`fireEvent` are async, setup in `src/test/setup.ts` mocks AsyncStorage, `renderWithTheme` in `src/test/render.tsx`), next to the code as `*.test.ts(x)`. Enrollment is built (see Security > Enrollment implementation; screen `src/app/enroll.tsx`, code in `src/enrollment/`, camera via `expo-camera`, deep link `splitcortex://enroll?url=...&code=...`, default URL `EXPO_PUBLIC_ENROLLMENT_URL`); the gateway connection, model download and engine adapter are built (below); the Android background service and boot start are built (native, compiled but not run on a device).
- **Node service (built, not run on a device)**: `src/runtime/NodeRuntime.ts` owns the gateway connection (`src/protocol/connection.ts`: wss + protobuf, mutual proof of possession against the gateway key **pinned at enrollment**, reconnect with jittered backoff up to 30 s, 60 s idle watchdog, answers pings; it never authenticates to a server whose proof does not match the pinned key), the model (`src/models/manager.ts`) and the engine (`src/engine`). The protocol types are generated from the gateway's proto (`pnpm gen:proto`, committed under `src/protocol/gen`); the handshake byte layout is in `protocol/handshake.ts` and must match `src/gateway/src/node_ws.rs`.
- **Models**: on `ModelAssignment` the node downloads the pool's single model from the control plane (`<enrollment URL>/node/models/<id>/file`) in 4 MiB `Range` requests streamed to disk piece by piece (never a whole body in memory: the Android JS heap is capped near 192 MB and buffering 8 MiB bodies ran out of memory), each signed with the device key (`Authorization: Node ...`, so the 60 s skew never breaks a long download), resumes from the `.part` file after a restart, verifies SHA-256 (native `File.digest`), deletes the previous model first (replace; there may not be room for two) and loads the new one. Status (none/downloading/loading/ready/failed) is reported to the gateway as `ModelState`; a re-sent assignment of the already-ready model is only re-reported.
- **Engine**: `Engine` interface (`src/engine/types.ts`), adapter `LiteRtEngine` over the community **`react-native-litert-lm`** (Nitro module, third party; only its README and API were read, **evaluate the code and run it on a real device before relying on it**; its postinstall only fetches the iOS framework, so the pnpm build script is left unapproved while iOS is not built). The module is `require`d lazily, so without the native build the app still runs and requests fail with a clear error. Each OpenAI request is self-contained: the history is flattened to a system prompt plus one user turn, and sampling/system settings are applied by reloading the model when they change (to be revisited on a device). One request at a time.
- **UI**: Home shows the service card (connection, model and download progress, counts, start/stop/restart) an **Open the web app** button (once enrolled: opens the default browser on the control plane host, the stored URL without `/api`; no webview, because Google sign-in is blocked in embedded webviews) and links to **Logs** (in-memory ring buffer of 500 lines, share/clear; states and counts only, never prompts or completions) and Settings. Settings has the **Service** toggles: *start at boot* (default on) and *connect and load the model on start* (default on).
- **Background service (Android, `modules/splitcortex-node-service`, a local Expo module in Kotlin, autolinked)**: `NodeService` is a foreground service of type `specialUse` (a boot receiver cannot start an activity on modern Android, and `dataSync` services cannot be started from boot on Android 15) with a partial wake lock, an ongoing low-priority notification, and it extends React Native's `HeadlessJsTaskService`, so it runs the JS task `SplitCortexNode` with no UI. `BootReceiver` starts it on `BOOT_COMPLETED` and after an app update when *start at boot* is on (the flag is mirrored into native SharedPreferences, default on, because no JS runs before the receiver). The headless task (`src/runtime/headless.ts`, registered from the custom entry `index.ts`, because after a boot no screen is ever rendered) calls `runtime.start()` (so: gateway connection, model download/load, serving) and stays pending until the runtime stops; if *connect and load on start* is off, or the device is not enrolled/approved, it stops the service at once. When the user opens the app the same JS runtime and the same singleton runtime are used (`runtime.start()` is idempotent). `runtime.start()` starts the service and `runtime.stop()` stops it, so the notification and wake lock exist exactly while the node serves. Android 13+: the app asks for the notification permission (without it the service still runs, only the notification is hidden). **Doze**: the service also holds a Wi-Fi lock (`WIFI_MODE_FULL_LOW_LATENCY`, high-perf before Android 10) next to the wake lock, and the app asks the user to exempt it from battery optimisation (the manifest declares `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`; native `isIgnoringBatteryOptimizations` / `requestIgnoreBatteryOptimizations` open the system dialog, falling back to the settings list). A card (`BatteryExemption`) on the home screen (until exempt) and in Settings (always) shows the state and the button; it re-reads when the app returns from the dialog. This needs the user's consent, it cannot be done silently. **Not run on a device**: check the boot start with a real reboot, that the exemption keeps the connection alive with the screen off, manufacturer task killers, and that the headless task and the foreground JS runtime really are the same runtime.
- **Android build requirements (found by building)**: `react-native-litert-lm` needs **minSdk 26** and its LiteRT-LM AAR is compiled with **Kotlin metadata 2.4.0**, while Expo SDK 58 / React Native 0.88 default to Kotlin 2.2.0, so the build failed twice (manifest merge, then Kotlin compile). `app.json` therefore has `expo-build-properties` with `minSdkVersion: 26` and `kotlinVersion: "2.4.0"` (applied by `expo prebuild`, so CI and local builds both get it; the whole app compiles with Kotlin 2.4). Verified: `./gradlew :app:assembleDebug` succeeds (about 22 minutes cold, four ABIs) and the merged manifest contains the service, the boot receiver and the permissions. Devices below Android 8 are no longer supported.
- **Compute backend and context window (built, not run on a device)**: `engine/compute.ts` (`ComputeEngine`) wraps the LiteRT engine and decides the backend (`cpu`|`gpu`) and context window (`maxContextTokens`) **per field: admin override (web app, per device, arrives as `NodeConfig`) > this app's setting (Settings: Compute Auto/CPU/GPU, Context: a number field, 512 to 131072 tokens, empty = automatic, saved on blur because every change reloads the model) > automatic**. Automatic backend: with a GPU driver (`getDeviceInfo().gpuAvailable`) and not on an emulator, the first load of a model file loads and benchmarks both (40 decode tokens, prefill excluded), takes the GPU only if it is >10 % faster (`GPU_MARGIN`) and remembers the answer per model file in AsyncStorage; otherwise CPU. Automatic context follows RAM (<4 GB: 2048, <10 GB: 4096, else 8192; unknown: the library default 4096). A forced GPU without a driver runs on the CPU; a failing load steps back (requested, CPU, CPU with the default window) instead of failing. A change of the effective settings reloads the model, after a running generation finishes; requests wait for a reload. What it runs on and the window are shown on the home screen and sent in `Telemetry.backend`/`max_context_tokens` (also right after a load or reload) so the gateway can route by context size. The bundle's own compiled cache length is not read yet (a too large window fails to load and steps back). Sampling parameters stay per request (not part of this).
- **Telemetry (native, same module)**: `getTelemetry()` returns the app's CPU share of the whole device (this app's own CPU time over wall time per core; Android blocks reading other apps' CPU), resident memory of the app (PSS, includes the mapped model), battery percent, charging and battery temperature (from the sticky battery broadcast). Sent to the gateway every 10 s with tokens/sec; unknown values use the protocol's sentinels. No iOS equivalent yet.
- Enrollment UI: accepts a typed short code (always) or a scanned QR (when a camera works), with an editable enrollment URL (the control plane / BFF, not the gateway). See Security for the protocol.
- **iOS (decided direction, nothing built or run on iOS yet)**: the app stays cross-platform and the engine, service and device-info interfaces must not assume Android. **An iOS node is foreground-only**: iOS has no foreground service and suspends the app shortly after it leaves the foreground (closing the socket), so it serves only while the app is open with the screen on (idle timer disabled), ideally charging. Do not rely on audio/VoIP/location tricks to stay alive (App Store rejection). Android is the always-on platform. LiteRT-LM has a Swift API (docs say from 0.12.0, Swift Package Manager, Metal GPU) but the overview marks it **Early Preview** (Kotlin and Python are Stable); re-check its state before building the iOS engine. iOS also kills memory-heavy apps (jetsam), so large models are riskier there. Secure Enclave only does P-256, not Ed25519: **decided: the node identity stays Ed25519, stored in `expo-secure-store` (software, exportable on a rooted device), no hardware-backed keys.** ECDSA P-256 would allow non-exportable keys on Android (StrongBox/Keystore) and iOS but changes the enrollment protocol and re-enrolls every node; switching later is possible, so revisit it only if hardware-backed keys become a requirement (cheapest before the gateway challenge-response exists).
- **Native code (open, to evaluate when the engine is built)**: third-party Expo/RN wrappers for LiteRT-LM exist (`react-native-litert-lm`, `expo-litert-lm`, `expo-ai-kit`), none official; evaluate them on a real device (read the code, check dependencies) behind our engine interface before writing our own module. A foreground-service library (Notifee / `react-native-notify-kit`, `react-native-background-actions`) must be tested for keeping a JS WebSocket alive with the screen off. CPU core count has no JS API, so reporting it needs a tiny local Expo module (not built; the enrollment currently sends no `cpuCores`).

## Original endpoint app rules (verbatim)

**Endpoint app (decided)**: React Native with Expo, TypeScript. It runs on the phone as the inference node and connects to the gateway.
- Dev setup only for now: run on a physical device. **No EAS builds**; build locally (`expo prebuild` / `expo run:android` or `expo run:ios`).
- LiteRT-LM needs native code, so Expo Go will not work. Use a local development build with a custom native module (Expo Modules API) wrapping LiteRT-LM. Keep that module behind the engine interface.
- The app must keep the TLS connection to the gateway alive while serving; mobile OS background limits (Android foreground service, iOS suspension) are a known risk to investigate early.
- **x86_64 emulator**: `react-native-litert-lm` hard-codes `abiFilters 'arm64-v8a'`, which breaks an x86_64 build (link errors on NitroModules symbols), although Google's `litertlm-android` AAR ships `x86_64` too. `src/node/patches/react-native-litert-lm.patch` (pnpm `patchedDependencies`) makes the filter follow `reactNativeArchitectures` (restricted to arm64-v8a/x86_64) and lets `LiteRTLMPackage` initialise the native module on an x86_64 primary ABI (it skipped init on anything but arm64, so `ModelStore` was never registered with Nitro). After changing the patch, delete `android/build/generated/autolinking` (it caches the package path). The x86_64 build compiles; the engine has not been run on an emulator.
- **Connection resume and gateway key rotation**: every chunk/done/error is numbered and kept per request (`outbox`, up to 20 000 frames, 60 s after the end); after a reconnect the node sends `Resume {request ids}`, and on `ResumeAck` resends what the gateway missed; ids the gateway does not list are dropped, `Cancel` also drops the frames. If the gateway stays unreachable for 40 s the running request is given up. Returning to the foreground reconnects at once (`reconnectNow`). The device trusts the pinned gateway key plus any key announced during a rotation (signed by a trusted key over its connection nonce, stored in `gateway.nextKeys`); when the gateway proves a next key, that key becomes the current one and the old is forgotten. It reports the key ids it trusts (`GatewayKeys`) after every `Ready`. Not run on a device.
- **More settings and enrollment details**: *Multi-token prediction (MTP)* passes `enableSpeculativeDecoding` to the engine (speculative decoding with the bundle's drafter, e.g. Gemma 4; the library ignores it for bundles without one, and a failed load retries without it). *Keep the screen on* sets `FLAG_KEEP_SCREEN_ON` on the visible activity through the native module (some Android devices only run the GPU at full speed with the app in the foreground and the display on, so the app has to stay open; it is re-applied when the app returns to the foreground and cleared when the service stops). Both are local settings with an admin override per device (`NodeConfig`, tri-state: the admin value wins, empty means the device's own). The home screen lists the organisation, pool, device name, device ID, key fingerprint, enrollment time, control plane URL and gateway URL; the organisation and pool names come from the enrollment response and are refreshed from `GET /node/me` (`enrollment/info.ts`) whenever the screen is focused, best effort. Not run on a device.
