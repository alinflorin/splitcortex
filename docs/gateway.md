# Gateway (`src/gateway`, Rust)

Rules summary is in [CLAUDE.md](../CLAUDE.md). Status: built.

## Layout and protocol

- tokio + axum 0.8 (WebSocket), sqlx (Postgres, plain connection for now), prost, ed25519-dalek. Own Docker context. Modules: `cache.rs` (config cache + change feed), `registry.rs` (live nodes, balancing, request table), `node_ws.rs` (node leg), `openai.rs` (client leg), `usage.rs`, `limits.rs`, `state.rs`, `config.rs`. `cargo test`; `cargo run -- keygen` prints a key pair.
- Env: `DATABASE_URL`, `GATEWAY_PRIVATE_KEY` (base64url Ed25519 seed), `PORT`, `LOG_LEVEL`, `USAGE_MAX_BUCKETS`, `USAGE_MAX_AGE_SECONDS`.
- Proto: `src/gateway/proto/splitcortex/node/v1/node.proto` (compiled at build time with `protox` + `prost-build`, no `protoc`). Node apps commit generated TS (`pnpm gen:proto`, needs `protoc`). Every binary WS frame is one `Envelope`; additive changes only.

## Node leg

- **Handshake on `GET /node`** (mutual proof of possession): node `ClientHello{node_id,nonce}`; gateway `ServerHello{nonce,signature}` = Ed25519 by gateway key over `splitcortex-gateway-hello-v1 \n node_nonce \n node_id` (node verifies against the pinned key before anything else); node `ClientAuth{signature}` over `splitcortex-node-hello-v1 \n server_nonce \n node_nonce \n node_id`; gateway `Ready`. ServerHello is sent for any node id, so an unknown id looks like a bad signature (socket closed, no reason). Org/pool come from the cached registered record, never the stream. Node must be `approved`; a newer connection of the same node replaces the older. `max_in_flight` = 1.
- **Models**: after `Ready` and on change the gateway sends `ModelAssignment` (id, name, size, sha256); one model per pool (`pool_models.pool_id` unique). The node downloads from the control plane (never via the gateway), replaces the old model, reports `ModelState`. Requests only go to nodes `READY` for the assigned model; a changed assignment clears readiness.
- **Live reconcile**: after every change batch and every 10 s the gateway closes sockets of deleted/unapproved/moved nodes and pushes assignment changes.
- **Engine settings per device**: admin overrides on the node (`nodes.compute_backend` cpu|gpu, `max_context_tokens`, `keep_screen_on`, `enable_mtp`; null = device decides; booleans travel in `NodeConfig` as `""`/`"on"`/`"off"`, empty/0 = no override), cached in `NodeRec`, sent as `NodeConfig` after `Ready` and on change. Node reports what it runs (`Telemetry.backend`, `max_context_tokens`) into `node_status`; `ModelState.modalities` (`image`/`audio`, set while READY) says what the loaded model accepts besides text (stored as `node_status.modalities`).
- **Status**: `node_status` written on connect/disconnect/telemetry (cpu/memory/battery/charging/temperature/tokens-per-sec every 10 s; sentinel values stored as null), refreshed every 15 s; on start an instance clears `connected` for rows with its own `gateway_id`.
- **Connection resume**: every `InferenceChunk`/`Done`/`Error` has a per-request `seq` (gateway drops repeats). If the socket drops while streaming, the request is kept 20 s (`RESUME_GRACE`); a request that produced nothing fails at once and is retried elsewhere. The node keeps generating and keeps every frame (up to 20 000, until 60 s after the end), and after `Ready` sends `Resume{request_ids}`; gateway answers `ResumeAck{request_id,received_seq}` for known ones, node resends above that, gateway sends `Cancel` for unknown ids; detached requests the node doesn't list fail. No new request goes to a resuming node (until `Resume` or 5 s). A node unreachable 40 s abandons its request. Resume across **different** instances is impossible (fails after grace). Node reconnect: exponential backoff + jitter 1–30 s, immediate on app foreground.

## Client leg (OpenAI edge)

- The `/v1` edge is also reachable on the web app host (`gateway.appIngress`, path `/v1` only) for the UI's Playground, same origin, so the gateway sends no CORS headers.
- `GET /v1/models` (union of the key's pools' models; adds `context_length` = smallest window among ready nodes when known), `POST /v1/chat/completions` (JSON or SSE; no `stream_options`, no tools). Auth `Authorization: Bearer sc_...`: sha-256 hex in cache, DB fallback on miss + 10 s negative cache; `last_used_at` written at most once a minute. OpenAI error shape.
- **Error messages are translated** by `Accept-Language` (en, ro; `src/i18n.rs`): `ApiError` carries a message key + arguments and the `localize` layer renders it per request (also on the internal listener; `forward_chat` passes the header on). The OpenAI `code`/`type` fields stay stable; text a node supplies is relayed as is.
- Failure before first token: retry once on another node. Mid-stream: stream ends with an error event (no silent restart, avoids double metering). Client disconnect sends `Cancel`.
- **Multimodal input (images, audio)**: `content` may be a string or an array of OpenAI parts: `text`, `image_url` (**base64 `data:` URL only**, JPEG/PNG/BMP/GIF; the gateway never fetches a URL) and `input_audio` (`{data: base64, format: wav|mp3|flac}`). Any other part type or format is refused with a clear `400` (`unsupported_content_type`, `unsupported_media_type`, `unsupported_media_url`, `invalid_base64`), never silently dropped; media only in `user` messages. Limits: 64 media parts and `GATEWAY_MAX_MEDIA_MB` (default **256** MiB) of decoded media per request (`413 media_too_large`); the body limit (media as base64 + 1 MiB, ≈ 342 MiB by default) is applied **after authentication** (the handler reads the body itself). Text files are not a wire type: clients paste them in as text. Mapping to the node protocol: `ChatMessage.content` always carries the joined text (an older node still sees it); `ChatMessage.parts` (`ContentPart` = text | `Media{mime_type, data}` image | audio) only when the message has media. Media goes **only to nodes that list the input in `ModelState.modalities`** (`registry.rs`: `IMAGE`/`AUDIO` bits, part of `eligible`, counted only while the model is ready). If ready nodes exist but none takes it: `400 unsupported_modality` (checked across instances through `node_status.modalities`; `peers_with_pools` filters on it too); no ready node at all stays `503`. `/v1/models` adds `input_modalities` (`text` + what its ready nodes accept) and `max_media_bytes` (not OpenAI format). Memory: the gateway holds a request about three times over (body, decoded media, protobuf copy), so size the pod for the limit times the concurrent large requests; lower the setting for small pods. Metering/context estimates: an image counts 256 tokens, audio 6.25 tokens per second (WAV length from its header, else 16 kB/s for mp3, 64 kB/s for flac); these are estimates like the char/4 text count. Gateway → node frames carry the media in one WebSocket message (the 1 MiB limit applies to node → gateway only); the media stays in the request and is never logged.
- **Tokens**: gateway counts one completion token per streamed piece and prompt tokens as chars/4 (no tokenizer yet); node-reported counts are ignored.
- **Context-aware routing**: needs ≈ prompt chars/4 + `max_tokens` (1 if absent); nodes with a smaller reported window are skipped (unknown = fits); if no ready node anywhere is large enough: `400 context_length_exceeded` (asks the DB for the largest reported window).

## Routing

- Key is scoped to the whole org or a set of pools (`api_keys.all_pools` or `api_key_pools`; org-wide also covers later pools). The gateway **resolves the pool from `model`** among the key's pools that have it assigned and ready, with eligible nodes (several: balance by in-flight load); none = `404`. A key whose pools were all deleted matches nothing. No pool-selecting headers/paths.
- Registry keyed by `(org, pool)`. Eligible = connected, healthy, model ready. Balancing per pool (`pools.balancing_type`): `weighted_p2c` (default: power of two choices on in-flight, weighted by measured tokens/sec), `least_in_flight`, `round_robin`, `random`. `serving_type` is `replicated` only.
- No eligible node: `503` + `Retry-After`; limits exceeded: `429` before any node is touched.
- The registry is per process; a request reaching an instance without a suitable node is forwarded (below). `NodeChannel` is the seam for NATS later.

## Rate limits

`requests_per_minute`, `tokens_per_minute`, `tokens_per_day` (UTC day), null = unlimited, on the org and on each key (`limit_*` columns; edited via `PATCH /organisations/:id` and `.../api-keys/:keyId`). Both must allow, else `429` `rate_limit_exceeded` with `Retry-After`. Prompt tokens counted at admission, generated tokens as streamed. Minute windows are **per instance** (N instances ≈ up to N× the limit); the daily total is re-read from `usage_records` every 10 s plus the local count. A forwarded request is checked only by the receiving instance.

## Several instances

- `gateway.replicas`. Each instance heartbeats `gateway_instances` (pod name, internal `POD_IP:8081`; rows >20 s ignored, 2 min deleted) and writes `node_status.gateway_id` for its nodes. If the receiving instance has no suitable node it finds peers holding nodes of the key's pools and forwards to `POST /internal/v1/chat/completions` on the **internal port** (not in Service/Ingress), `Authorization: Bearer <SHA-256 derived from the identity key>` + key hash in `X-Sc-Key`; the serving instance meters; response (incl. SSE) streams back unchanged; peer `502`/`503` = try next peer. A node connecting to one instance is closed on the others within 15 s. Benchmarks run on the instance holding the node.
- **Graceful drain** on SIGTERM: set `draining`, fail `/readyz`, delete own `gateway_instances` row, keep serving `DRAIN_DELAY_SECONDS` (5), then refuse new chats (`503`) and node connections, close idle nodes, wait until no request is running (max `DRAIN_TIMEOUT_SECONDS`, default 3600, chart `gateway.drain.timeoutSeconds`; `terminationGracePeriodSeconds` = timeout + delay + 60), flush usage, mark nodes disconnected, exit. Old pods linger in rolling updates (don't block `helm upgrade --wait`). No benchmarks while draining.
- No shared store or broker needed: presence in Postgres, forwarding is direct HTTP. Redis/NATS only ever for that, never for config or the live registry.

## Benchmarks

Control plane creates a `benchmarks` row + a `pending` `benchmark_results` row per online node (`POST /organisations/:org/pools/:pool/benchmarks`, admins, one at a time per pool). Every 4 s each gateway claims pending results of its nodes (`FOR UPDATE SKIP LOCKED`), waits up to 90 s for the node to be free, runs one fixed platform prompt (96 tokens max, temperature 0), records time to first token, total time, pieces, tokens/s after first token. Unrun results older than 3 min fail. Prompts are platform-supplied, not metered.

## Gateway identity key and rotation

- **Creation**: once, by a Helm hook Job (`templates/gateway-identity-job.yaml`, `pre-install,pre-upgrade`, own ServiceAccount/Role limited to Secrets). Init container (gateway image, `gateway keygen --out /keys/keys.env`, mode 0600) generates the pair; main container (`alpine/k8s`, kubectl) creates **`gateway-identity`** (`private-key`, mounted only by the gateway as `GATEWAY_PRIVATE_KEY`) and **`gateway-public-key`** (`public-key`, read by the control plane as `GATEWAY_PUBLIC_KEY`, handed to devices at enrollment). If both exist it does nothing (upgrades never rotate); if only one exists it fails loudly. The Secrets are not Helm-managed and survive `helm uninstall` (a new key orphans every pinned device); delete both by hand to start a new identity and re-enroll. Private key never in logs, Job env or the DB. Under Tilt it's a plain Job run via `cargo run -- keygen` that gateway and control plane wait for.
- **Rotation** (two-key overlap; one Helm stage per `helm upgrade` via `gateway.rotation.stage`, pre-upgrade Job `gateway-rotation`): (1) `prepare` creates `gateway-identity-next` / `gateway-public-key-next`; gateways read `GATEWAY_NEXT_PRIVATE_KEY` and announce the next public key in `Ready.next_gateway_key`, signed by the current key over the device's connection nonce (no replay); devices verify with their pinned key and trust both, and report trusted key ids (`GatewayKeys`, first 8 bytes of SHA-256) into `node_status.gateway_keys`. (2) `kubectl exec deploy/gateway -- gateway rotation-status` shows counts and when promoting is safe (offline devices learn the key when they return; wait or re-enroll them). (3) `promote` keeps the old pair as `-previous` (rollback), makes next current, deletes `-next`; gateways and control plane restart (annotation `splitcortex.io/gateway-rotation`). A device seeing a ServerHello signed by its trusted next key adopts it and forgets the old. (4) Set the stage back to empty. Stages are idempotent. A device offline for the whole overlap must re-enroll. Not run in a cluster.

## Config cache and metering

- **Cache (no Redis)**: node records, pools, models, API key hashes and limits in process memory. The control plane writes a `config_changes` row (seq, entity type/id, org id) in the same transaction as every config change, then `NOTIFY` (wake-up only, may be lost; a `seq` jump = missed notification, catch up). Startup: `LISTEN` first, then consistent snapshot + `seq`, then catch up. One consumer task wakes on `NOTIFY`, on `LISTEN` reconnect, or a 30 s backstop; reads changes after its cursor with a 200-row overlap (seq may commit out of order), de-duplicates by entity, **re-fetches the current row** (never applies diffs; missing = delete), swaps it in; idempotent. A gap or disconnect longer than retention = full resync.
- Side effects: deleted/revoked/re-keyed/unapproved node has its socket closed immediately; pool change moves its registry entry; revoked key rejects new requests at once.
- DB unreachable: keep serving last known config, expose feed lag, may fail closed after a configurable max staleness (`503` + `Retry-After`; **not built yet**).
- **API keys**: cache maps `hash(key)` → org, pool, limits, status. Keys are long random secrets with a readable prefix and key id; SHA-256 suffices; compare in constant time. Only hashes stored/cached. Miss = one DB lookup (new keys work at once) with a short negative cache.
- **Usage**: counters keyed (minute bucket, org, pool, key id, model) with tokens in/out, requests, errors, flushed every 5 s (backoff to 60 s) in one transaction with an additive upsert (`ON CONFLICT DO UPDATE SET x = x + EXCLUDED.x`) and a unique batch id in `usage_flushes` (an ambiguous commit's retry becomes a no-op: no double counting). Failed flushes keep counters in memory, retried with backoff + jitter without blocking requests. **Fail closed (decided)**: `503` + `Retry-After` for new inference when the bounded buffer is full or the oldest unflushed bucket exceeds the max age (default ~10 min); recovers automatically. A drop-oldest mode (loses oldest buckets, logs it) exists for self-hosted/LAN. Flush on SIGTERM; a hard crash loses at most one interval. Flush lag/failures/buffer size are logged (never prompts, completions or keys).
- **Per-organisation metrics (decided)**: `metrics.rs` writes `pool_metrics` (per minute, org and pool: requests refused by limits `rate_limited`, requests no node could serve `unavailable`, peak in-flight, latency and time-to-first-event **histograms** as counts per bucket, bounds in `BOUNDS_MS`, shared with `dto/metrics.ts`) and `node_metrics` (per minute and node: the last `Telemetry` of the minute) to Postgres. Requests, errors and tokens stay in `usage_records`. Counted where the node is (a forwarded request is counted by the instance holding the node), 429/unavailable at the instance that received the request, pool = the first pool serving the model. Buffered in memory, flushed every 20 s (backoff to 120 s) in one transaction with an additive upsert (histograms added bucket by bucket with `unnest ... with ordinality`, peak = `greatest`); **not fail-closed** (a full buffer drops the oldest minute and logs it), never one row per request, no gateway-wide causes (draining, metering behind) and no instance ids in any row. Retention: control plane CronJob (7 days). Read by `GET /api/organisations/:orgId/metrics`.
- **Prometheus/OTel deferred** (the per-organisation metrics above are not Prometheus). If added: never key or org as a metric label, never prompts/completions in spans.
- **Not built yet**: config-staleness fail-closed, tokenizer-based counting, `node_status` model progress, shared per-minute limit across instances.

## Audit events

`audit.rs` writes the gateway's events to `audit_logs` (the control plane writes the rest, see docs/control-plane.md): `node.connected`, `node.disconnected`, `node.connect_rejected` (not approved / bad signature; only for known node ids), `api_key.rejected` (revoked or expired key), `limit.exceeded`. **Never one row per request.** Events are buffered (5000, oldest dropped with a warning) and flushed every 5 s in one transaction straight to Postgres; unlike usage this is **not fail-closed**, audit never blocks serving. Repeats of the same (organisation, action, entity) within 60 s are folded: the next row carries `metadata.repeats`. Unknown key hashes and unknown node ids have no organisation and are not recorded; neither is drain (instance-wide). No IP yet (the gateway does not read forwarded headers). Rows of a deleted organisation are skipped.

Since then the owner has run nodes on real hardware (details not recorded). Not run in a cluster.
