# Gateway: config cache, usage metering, routing

Details for the Rust gateway (`src/gateway`). Summary and hard rules are in [CLAUDE.md](../CLAUDE.md).

## Implementation (built)

- **Crate `src/gateway`** (own Docker build context, nothing outside the folder is needed): tokio + axum 0.8 (WebSocket), sqlx (Postgres, plain connections for now; add a TLS feature when the database requires it), prost for protobuf, ed25519-dalek. Modules: `cache.rs` (config cache + `config_changes` feed, LISTEN/NOTIFY, 30 s backstop, 200-row overlap re-read, full resync on a log gap), `registry.rs` (live nodes, balancing, request table), `node_ws.rs` (the node leg), `openai.rs` (the client leg), `usage.rs` (metering and fail-closed), `state.rs`, `config.rs`. Run `cargo test`; `cargo run -- keygen` prints a new identity key pair. Environment: `DATABASE_URL`, `GATEWAY_PRIVATE_KEY` (base64url Ed25519 seed), `PORT`, `LOG_LEVEL`, `USAGE_MAX_BUCKETS`, `USAGE_MAX_AGE_SECONDS`.
- **Protocol source of truth: `src/gateway/proto/splitcortex/node/v1/node.proto`** (inside the gateway folder so its Docker context stays `src/gateway`). The gateway compiles it at build time with `protox` + `prost-build` (no `protoc` needed). The node app commits a generated TypeScript copy (`src/node/src/protocol/gen`, regenerate with `pnpm gen:proto` there, needs `protoc`). Every binary WebSocket frame is one `Envelope`; additive changes only.
- **Handshake on `GET /node`** (mutual proof of possession, no secret on the wire): node `ClientHello {node_id, nonce}`; gateway `ServerHello {nonce, signature}` where the signature is Ed25519 by the gateway key over `splitcortex-gateway-hello-v1 \n node_nonce \n node_id` (the node verifies it against the key pinned at enrollment and never authenticates to anything else); node `ClientAuth {signature}` over `splitcortex-node-hello-v1 \n server_nonce \n node_nonce \n node_id` by its device key; gateway `Ready`. The ServerHello is sent for any node id, so an unknown id looks like a bad signature (the socket is simply closed, no reason given). Org and pool come from the registered record in the cache, never from the stream. The node must be `approved`; a newer connection of the same node replaces the older one. Nodes run one request at a time (`max_in_flight` = 1).
- **Gateway identity key**: created **once by a Helm hook Job** (`templates/gateway-identity-job.yaml`, `pre-install,pre-upgrade`, with its own ServiceAccount/Role limited to Secrets of the namespace). An init container (the gateway image, `gateway keygen --out /keys/keys.env`, file mode 0600, nothing printed) generates the Ed25519 pair; the main container (`alpine/k8s`, `kubectl`) creates two Secrets in one request: **`gateway-identity`** (`private-key`, base64 seed, mounted only by the gateway as `GATEWAY_PRIVATE_KEY`) and **`gateway-public-key`** (`public-key`, read by the control plane as `GATEWAY_PUBLIC_KEY` and handed to devices at enrollment). If both Secrets exist the Job does nothing, so upgrades never rotate the key; if only one exists it fails loudly. The Secrets are not Helm-managed, so they survive `helm uninstall` (a new key would orphan every pinned device); delete both by hand to start a new identity and re-enroll the devices. The private key never appears in a log, an env var of the Job, or the database; the gateway writes nothing about its identity. Under Tilt it is a plain Job (`gateway-identity`, run through `cargo run -- keygen`) that the gateway and the control plane wait for. Rotation is built as a two-key overlap, see **Gateway key rotation** below.
- **Models on nodes**: the gateway sends `ModelAssignment` (id, name, size, sha256) after `Ready` and whenever the pool's model changes; **one model per pool** (`pool_models.pool_id` is unique). The node downloads it from the control plane (never through the gateway), replaces the previous model, and reports `ModelState`. A request is only routed to a node that reports `READY` for the assigned model; a changed assignment clears readiness until the node reports again.
- **Live reconcile**: after every applied change batch (and every 10 s) the gateway closes sockets of deleted, unapproved or moved nodes and pushes assignment changes.
- **OpenAI edge**: `GET /v1/models`, `POST /v1/chat/completions` (JSON or SSE; `stream_options` and tools are not supported). Auth is `Authorization: Bearer sc_...`, sha-256 hex looked up in the cache, with a DB fallback on a miss and a 10 s negative cache; `last_used_at` is written at most once a minute per key. Errors use the OpenAI error shape. Pre-first-token node failure retries once on another node; a failure mid-stream ends the stream with an error event. A client that disconnects cancels the node's work (`Cancel`). **Tokens**: the gateway counts one completion token per streamed piece and estimates prompt tokens as characters / 4 until it has a tokenizer; node-reported counts are ignored.
- **Per-device engine settings**: the control plane stores admin overrides on the node (`nodes.compute_backend` `cpu`|`gpu`, `nodes.max_context_tokens`; null = the device decides). The gateway caches them in `NodeRec` and sends a `NodeConfig` after `Ready` and whenever they change (reconcile loop; empty/0 = no override). The node reports what it actually runs (`Telemetry.backend`, `max_context_tokens`), stored in `node_status`. **Context-aware routing**: a request needs about prompt chars/4 + `max_tokens` (1 when absent); nodes whose reported window is smaller are skipped (unknown window = assumed to fit); if no ready node anywhere is large enough the client gets `400 context_length_exceeded`. `/v1/models` adds `context_length` (the smallest window among ready nodes) when known.
- **Metering and status**: usage buckets flush every 5 s (backoff to 60 s) in one transaction with a `usage_flushes` batch id and fail closed (`503`) as described below; flush on SIGTERM. `node_status` is written on connect/disconnect/telemetry (nodes send cpu/memory/battery/charging/temperature/tokens-per-sec every 10 s; unknown values arrive as sentinels, see the proto, and are stored as null) and refreshed every 15 s for connected nodes; on start the instance clears the `connected` flags of the rows it held before (`gateway_id` = its own id).
- **Not built yet**: config-staleness fail-closed, tokenizer-based counting (prompt tokens are chars / 4), `node_status` model progress, and a shared per-minute limit across instances.
- **Rate limits (built)**: `requests_per_minute`, `tokens_per_minute` and `tokens_per_day` (UTC day), nullable = unlimited, on the organisation and on each API key (`limits.rs`; columns `limit_*` on `organisations` and `api_keys`, cached like everything else; the control plane edits them with `PATCH /organisations/:id` and `PATCH /organisations/:id/api-keys/:keyId`). Both the organisation's and the key's limits must allow a request, otherwise `429` (`rate_limit_exceeded`, with `Retry-After`) before any node is touched. Prompt tokens are counted when the request is admitted, generated tokens as they stream. Minute windows are fixed wall-clock minutes **per gateway instance** (so with N instances the effective rate is up to N times the limit); the daily total is re-read from `usage_records` every 10 s (plus what this instance counted since), so instances see each other's flushed usage. A request forwarded to another instance is checked by the instance that received it, not again by the one that serves it.
- **Connection resume (built)**: every `InferenceChunk`/`Done`/`Error` carries a per-request `seq`; the gateway drops repeats. If a node's socket drops while a request is **streaming**, the request is kept for 20 s (`RESUME_GRACE`) instead of failing; a request that has produced nothing yet fails at once and is retried on another node, as before. The node keeps generating and keeps every frame of the request (up to 20 000, until 60 s after it ended). On reconnect it sends `Resume {request_ids}` right after `Ready`; the gateway answers `ResumeAck {request_id, received_seq}` for the ones it still tracks (the in-flight slot moves to the new connection), the node resends what is above `received_seq`, and the gateway sends `Cancel` for ids it does not know. Detached requests the node does not list fail. A new request is not sent to a node that is still resuming (until its `Resume` or 5 s). While a node is unreachable for 40 s the node gives up its running request. The client sees only a pause (SSE keeps the stream open). A node that reconnects to a **different** instance cannot resume (the request lives in the first one's memory): it fails after the grace period. The node also reconnects with exponential backoff and jitter (1 s up to 30 s) and immediately when the app returns to the foreground.
- **Several gateway instances (built, no extra software)**: `gateway.replicas` (rolling updates, nodes reconnect when a pod goes). Each instance heartbeats a row in `gateway_instances` (its pod name and internal `POD_IP:8081` address; rows older than 20 s are ignored, 2 min deleted) and writes its id in `node_status.gateway_id` for the nodes it holds. A client request is authenticated and limit-checked by whichever instance receives it. If that instance has a suitable node (ready, free, context fits) it serves the request; otherwise it looks up the other live instances that hold connected nodes of the key's pools (`node_status` join `gateway_instances`), and forwards the original request to one, `POST /internal/v1/chat/completions` on the **internal port** (not in the Service or the Ingress), with `Authorization: Bearer <token>` (a SHA-256 derived from the identity key, which every instance holds, so there is nothing extra to distribute) and the key hash in `X-Sc-Key`. The serving instance meters the usage and answers; the response (including SSE) is streamed back unchanged. `502`/`503` from a peer mean "no node here" and the next peer is tried. The `context_length_exceeded` check asks the database for the largest reported window when the local nodes are too small. A node that connects to one instance is closed on the others (they notice through `node_status.gateway_id` within 15 s). `ModelAssignment` and `NodeConfig` are pushed by each instance to its own nodes from its own cache. Benchmarks run on the instance that holds the node. On graceful shutdown the instance marks its nodes disconnected and leaves the directory.
- **Benchmarks (built)**: the control plane creates a `benchmarks` row and one `benchmark_results` row (`pending`) per online node of the pool (`POST /organisations/:org/pools/:pool/benchmarks`, admins; one at a time per pool). Every 4 s each gateway claims pending results of the nodes it holds (`FOR UPDATE SKIP LOCKED`), waits for the node to be free (up to 90 s), runs one fixed platform prompt (96 tokens max, temperature 0) and records time to first token, total time, pieces generated and tokens/s after the first token. Results older than 3 minutes that nobody ran fail ("not available in time"). Benchmark prompts are platform-supplied, never customer data, and are not metered.
- **Gateway key rotation (built)**: devices pin the gateway's public key, so a new key is introduced next to the old one and promoted only when every device trusts it. `gateway.rotation.stage` (Helm value, one stage per `helm upgrade`, a pre-upgrade hook Job `gateway-rotation` with its own ServiceAccount): (1) `prepare` creates the **next** key pair in `gateway-identity-next` / `gateway-public-key-next`; the gateways read `GATEWAY_NEXT_PRIVATE_KEY` (optional Secret ref) and announce the next public key in `Ready.next_gateway_key`, signed by the current key over the device's connection nonce (so it cannot be replayed); a device verifies the signature with the key it pinned and then trusts both. Every device reports the key ids it trusts (`GatewayKeys`, first 8 bytes of the SHA-256 of each key) into `node_status.gateway_keys`. (2) Check progress with `kubectl exec deploy/gateway -- gateway rotation-status` (counts only: approved devices, how many trust the next key, how many never reported; it says when promoting is safe; devices that are offline learn the key when they come back, so wait for them or accept re-enrolling them). (3) `promote` keeps the old pair as `gateway-identity-previous` / `gateway-public-key-previous` (rollback), makes the next key current, deletes the `-next` Secrets; the gateways and the control plane restart (pod annotation `splitcortex.io/gateway-rotation` changes with the stage, and the control plane reads the public key from the Secret at start). A device that connects to the new key sees a ServerHello signed by its trusted next key, makes it its current key and forgets the old one. (4) Set the stage back to empty. Both stages are idempotent. A device that was offline for the whole overlap has to be enrolled again. The private keys never appear in a log or a Job environment. Not run in a cluster.
- **Verified**: unit tests (`cargo test`) and a scripted run against a real Postgres (migrations applied): handshake with a wrong key rejected, gateway proof valid, assignment pushed, non-stream and SSE chat, unknown model 404, usage row written, node revoked closes its socket. Not run in a cluster or with a real device.

## Config cache and usage metering

- **Gateway config cache (decided)**: the gateway keeps node records, pools, models, API key hashes and limits in its own process memory. **No Redis**; the live registry of connected nodes holds socket handles and is in-process by nature. Sync from the control plane's database:
  - The control plane writes a row to a `config_changes` table (seq, entity type, entity id, org id) in the same transaction as every config change. After commit it sends a Postgres `NOTIFY` (push, wake-up only; notifications may be lost) whose payload carries the new `seq`. A `seq` jump versus the gateway's cursor means a missed notification and triggers an immediate catch-up.
  - On startup the gateway does `LISTEN` first, then reads a consistent snapshot and its change `seq`, then catches up from that `seq`.
  - A single consumer task wakes on `NOTIFY`, on `LISTEN` reconnect (immediate catch-up), or on a 30s backstop poll, reads changes after its last `seq` with a small overlap window (sequence values can commit out of order), de-duplicates by entity, **re-fetches the current row** (never applies diffs; a missing row means delete), and swaps it into memory. Re-applying is idempotent.
  - If the gateway sees a gap, or was disconnected longer than the log retention, it does a full resync.
  - Applying a change has side effects on live state: a deleted, revoked, re-keyed or unapproved node has its socket closed immediately; a pool change moves its registry entry; a revoked API key rejects new requests at once.
  - If the database is unreachable the gateway keeps serving the last known config, exposes the feed lag as a metric, and may fail closed after a configurable maximum staleness (new inference requests get `503` with `Retry-After`, like the usage flush fail-closed rule; it recovers automatically once the feed catches up).
  - **API keys in memory**: the cache maps `hash(key)` to org, pool, limits and status. Keys are long random secrets with a readable prefix and a key id (for display and revocation), so a fast hash (SHA-256) is sufficient; compare in constant time. Only hashes are ever stored or cached, never the secret. A cache miss falls back to one database lookup (so a newly created key works immediately, before the change event arrives), with a short negative cache to blunt invalid-key floods. Revocation arrives through the change feed and takes effect for new requests at once.
  - Usage counters and rate-limit state (see **Rate limits**) are also in gateway memory, flushed to `usage_records` in batches (limits are approximate across instances within the flush interval).
  - Usage records are the only metering store: counters keyed by (minute bucket, org, pool, key id, model) with tokens in/out, requests and errors, flushed with an additive upsert (`ON CONFLICT DO UPDATE SET x = x + EXCLUDED.x`) so several instances add up. The gateway counts tokens itself; node-reported counts are never trusted for metering. **Prometheus and OpenTelemetry are deliberately deferred** (decided not to add them yet); if added later, never use API key or org as a metric label, and never put prompts or completions in spans.
  - **Usage flush failures and retries**: a failed flush never drops counters.
    - Each flush is one transaction. Unflushed counters stay in memory and are merged into the next batch; retry with exponential backoff and jitter, never blocking the request path.
    - Each batch carries a unique batch id recorded in the same transaction (e.g. a `usage_flushes` table with a unique constraint). If a commit outcome is ambiguous (connection dropped after COMMIT), the retry hits the constraint and becomes a no-op, so the additive upsert cannot double count.
    - The in-memory buffer is bounded and sized to ride out ordinary database failovers (tens of minutes of traffic; a minute bucket is a few hundred bytes). **Default policy (decided): fail closed.** The gateway returns `503` with `Retry-After` for new inference requests as soon as either the buffer is full or the oldest unflushed bucket is older than a configurable maximum age (default ~10 minutes, like the config feed's maximum staleness), so no unmetered traffic is served and nothing is lost. It recovers automatically once a flush succeeds. A deployment that prefers availability over exact billing (self-hosted, LAN) can switch to drop-oldest via config, which drops the oldest minute buckets and logs the loss.
    - Flush on graceful shutdown (SIGTERM). A hard crash loses at most one flush interval of counters, the same approximation accepted for limits.
    - Flush lag, failure count and buffered bucket count are logged now (never prompts, completions or key material), and become metrics if Prometheus is added later.
  - A shared store or broker is not needed for multi-gateway: presence lives in Postgres (`gateway_instances`, `node_status.gateway_id`) and forwarding is direct HTTP between instances. Redis/NATS would only ever be considered for that, never for config or the live registry.

## Routing

- **Routing (gateway)**: API key hash, then org, limits and target pool, then a node from the in-memory live registry.
  - **An API key is scoped to the whole organisation or to a set of pools** (`api_keys.all_pools`, or rows in `api_key_pools`; an org-wide key also covers pools created later). The OpenAI format stays unchanged: clients only change base URL and key, and the gateway **resolves the pool from the request's `model`**: among the pools the key may use that have the model assigned and ready, pick one that has eligible nodes (if several do, balance across them by in-flight load); none serves it, `404` unknown model. `/v1/models` lists the union of the models of the key's pools. A key whose pools were all deleted matches nothing. Extra headers/paths to choose a pool are not used.
  - The live registry is keyed by `(org, pool)`. A node's org and pool come from its registered record (loaded from the database after proof of key possession), never from messages on the stream.
  - Eligible nodes are connected, healthy, have the requested model ready and have credits. Choose according to the pool's **balancing type** (`pools.balancing_type`, editable per pool): `weighted_p2c` (default: power-of-two-choices on in-flight requests, weighted by measured tokens/sec, since devices vary a lot), `least_in_flight`, `round_robin` or `random`. The pool's `serving_type` is `replicated` (the only value; sharding is future work behind the placement abstraction).
  - Failures: node drops before the first token, retry once on another node; drops mid-stream, end the stream with an error (no silent restart, to avoid double metering); no eligible node, `503` with `Retry-After`; limits exceeded, `429` before any node is touched.
  - The registry is per process: each instance holds its own nodes. A request that reaches an instance without a suitable node is forwarded to one that has (see **Several gateway instances**). `NodeChannel` stays the seam for replacing that forwarding with NATS or similar later.
