# Control plane implementation

Details for `src/control-plane`. Summary in [CLAUDE.md](../CLAUDE.md).

- **Control plane implementation (decided, `src/control-plane`)**: Fastify 5 + `fastify-type-provider-zod` (zod 4), PostgreSQL via **Drizzle ORM** (`drizzle-orm` + `pg`; schema in `src/db/schema.ts` is TypeScript but plain SQL migrations are generated by `drizzle-kit generate` into `drizzle/` and committed, so the Rust gateway can read the same tables with its own SQL; never hand-edit applied migrations). Entities so far: organisations, memberships (owner/admin/member), pools, `usage_records` + `usage_flushes` (metering store, **written by the gateway only**; `pool_id`/`key_id` have no foreign keys on purpose so history outlives deleted pools and keys; the control plane only reads them), `config_changes` (the gateway feed; `recordConfigChange` inside the transaction, `notifyConfigChange` after commit). DTOs are zod schemas in `src/dto` (**no shared package**: the UI copies the schemas it needs; keep them in sync by hand). Every route validates params/body/response with them and is documented in OpenAPI; **Swagger UI at `/api/docs`** (`/api/docs/json` for the spec); its Authorize button signs in through Dex (authorization code + PKCE with the public `splitcortex-ui` client, whose Dex `redirectURIs` therefore include `<web app origin>/api/docs/static/oauth2-redirect.html` in every environment; a pasted bearer token also works). All public routes live under the `/api` prefix (the ingress does not strip it); probes `/healthz` (liveness) and `/readyz` (DB) are at the root. Auth: `Authorization: Bearer <Dex token>` verified with `jose` against the Dex JWKS (issuer = `dex.config.issuer`, audience = `splitcortex-ui`; the JWKS URL defaults to the in-cluster Dex service so no public TLS is needed from the pod); there is **no users table** (Dex owns identities; the user is read from the token claims, `GET /api/me` echoes them) and memberships reference the lowercased token email as plain text. Tenant checks go through `requireOrgRole` (non-members get 404). The ingress serves `/api` on the **web app host** (same origin as the SPA, so no CORS). Validation messages in shared schemas are i18n keys.
- **Org/pool/member API (decided)**: organisations (get/update/delete; delete is owner-only and records a config change for each cascaded pool so the gateway drops them), members (list/add by email/change role/remove or leave) and pools (get/update/delete) are done, plus `GET /api/organisations/:orgId/usage` (any member; `from`/`to` capped at 92 days, `granularity` hour|day, optional `groupBy` pool|key|model and `poolId`/`model` filters). Role rules: owners manage everyone; admins only manage plain `member`s and cannot hand out a higher role; anyone may leave; the **last owner can never be demoted or removed** (owner rows are locked `FOR UPDATE` in the transaction). Route tests run against the real migrations on in-process Postgres (**PGlite**, `src/test/harness.ts`), no external database needed. Also done: pool settings (serving/balancing type), **nodes** (`nodes`: registered devices; list per pool, view, approve/rename, revoke, **per-device engine overrides** (`PATCH` `computeBackend` `cpu`|`gpu`|null and `maxContextTokens` 512..131072|null, admin only, recorded as a `node` config change so the gateway pushes it to the device; migration 0006); **created by enrollment, there is no manual create endpoint**) and **`node_status`** (live CPU/memory/battery/temperature/in-flight/tokens-per-sec plus the `backend` and `max_context_tokens` the engine actually runs with, **written by the gateway only**; a node is online only while `connected` AND the row is under 60 s old, so a crashed gateway cannot leave nodes looking online; stale telemetry is not shown), and **models** (below; **one model per pool**: `pool_models.pool_id` is unique, `PUT /organisations/:orgId/pools/:poolId/models/:modelId` replaces the pool's current model, the list endpoint returns at most one, migration 0005 keeps only the newest assignment of existing pools). Deleting a pool or organisation records `node` changes for the cascaded nodes so the gateway closes their sockets. The pool DTO carries `onlineNodes` (approved nodes that are connected and under 60 s old, one query per request in `routes/pools.ts`). **API keys** (`api_keys`, `api_key_pools`; `routes/api-keys.ts`): admin/owner only, `GET/POST /organisations/:orgId/api-keys`, `DELETE .../:keyId` (soft revoke, idempotent). Token `sc_` + 32 random bytes base64url, shown once in the create response; only `sha256(token)` (hex) is stored plus a 10-character display prefix. Optional expiry (must be in the future), `created_by`, `last_used_at` (written by the gateway), `revoked_at`. Create, revoke, a deleted pool (cascades the scope link) and a deleted organisation all record an `api_key` change so the gateway drops or refreshes the key; the gateway checks `revoked_at`/`expires_at` itself. Enrollment is done (below). Still missing: benchmarks.
- **Models and object storage (decided)**: models are organisation-scoped (`models`, `pool_models`; unique name per org; only `.litertlm`, max 32 GiB). Files live in an **S3-compatible bucket; Garage**, single node, the `garage` Helm subchart 2.5.0 from `https://charts.derwitt.dev` (a thin wrapper of upstream Garage; image overridden to the multi-arch `dxflrs/garage`, replication factor 1; credentials random in our `garage-credentials` Secret: `rpcSecret`, `token`, `access-key`, `secret-key`; the subchart installs a ClusterRole for its Kubernetes discovery CRD). **Garage is internal only: no ingress, no public S3 host, no CORS** (earlier design had browsers PUT to presigned URLs; replaced so storage is never exposed). The subchart bootstraps nothing, so a **Job `garage-bootstrap` (plain Job on first install, retrying about 10 minutes until Garage answers; `post-upgrade` hook afterwards; control plane image, `storage/bootstrap-cli.ts`) bootstraps Garage** through the admin API (`garage-admin:3903`, ClusterIP): layout for the node, ImportKey, bucket, AllowBucketKey; idempotent, retries while Garage settles, a plain Job under Tilt that the control plane depends on. Only that Job holds the admin token (API replicas never do, so replicas cannot race). Without S3 configuration the model endpoints answer 503. **Uploads pass through the control plane, streamed, never buffered**: `POST /models/uploads` returns `{model, partSize, partCount}` (8 MiB parts, grown for huge files to stay under 10,000), the browser `PUT`s each part as `application/octet-stream` to `/models/:id/parts/:n` (Content-Length must equal the expected part size; the request is piped into S3 `UploadPart`; returns the ETag), then `POST /models/:id/complete` verifies the stored size (mismatch deletes the object and fails the model). Parts are small because Traefik's default 60 s request read timeout applies to each (no entryPoint timeout changes). **Hugging Face URLs** are mirrored once by an in-process worker (`models/mirror.ts`, DB-claimed with `FOR UPDATE SKIP LOCKED`, stale claims recovered after 2 min, progress heartbeat that doubles as cancellation): only `https` on `huggingface.co`/`*.hf.co`, redirects followed manually and re-checked each hop (SSRF), the optional `HF_TOKEN` is sent to `huggingface.co` only, the file is hashed (sha256) while streaming and size-checked. Nodes never talk to Hugging Face. **Nodes download models from the control plane directly (decided, built)**, never through the gateway and never from object storage: `GET /api/node/models` lists the ready models of the calling node's pool (`id, name, fileName, sizeBytes, sha256`) and `GET /api/node/models/:modelId/file` streams the file (`Accept-Ranges`, a single `Range` per request so interrupted downloads resume; `206`/`416`; `X-Content-SHA256`/`ETag` when the hash is known, the node verifies it). A node only sees ready models assigned to its own pool (anything else is a generic 404). **Device authentication (`plugins/node-auth.ts`)**: `Authorization: Node <nodeId>.<unixSeconds>.<signature>`, an Ed25519 signature by the key registered at enrollment over `splitcortex-node-request-v1\nMETHOD\npath\nunixSeconds` (path without query, as received, so including `/api`); clock skew up to 60 s; unapproved or deleted (revoked) nodes fail at once; every failure is the same 401. No secret is sent and the same scheme can be reused for other device-facing routes. A captured request can only be replayed against the same method and path within the skew window. Large files flow through the control plane (stream, no buffering). **Abandoned uploads** are swept by the CronJob `control-plane-sweep` (chart `controlPlane.sweep`: schedule, `maxAgeHours` default 24, same image and env as the API; `storage/sweep.ts`, entry `storage/sweep-cli.ts`): models still `uploading` after the max age are deleted (config change recorded) and their multipart upload aborted, and open multipart uploads older than the max age that no model owns (and that belong to no model being mirrored) are aborted. An active upload running longer than the max age is therefore cut off.
- **Migrations**: `controlPlane.migrate` runs `dist/db/migrate.js`: on first install as a plain (non-hook) Job, because a post-install hook would deadlock (hooks wait for every workload to be ready and the gateway and control plane cannot be ready before the schema exists; they crash-loop until the Job finishes); on upgrade as a `pre-upgrade` hook Job, so the schema is updated before a new version rolls out (the script retries while Postgres is down). Under Tilt it is a plain Job (`control-plane-migrate`) that `control-plane` depends on; the dev image runs it through `tsx`. New migration files are not live-synced, so Tilt rebuilds the image and re-creates the Job.
- Still open: a Cargo workspace for the gateway, PAKE library availability in Node (server side) and React Native (device side), see Security.
- **Rate limits and benchmarks (built)**: `organisations` and `api_keys` have nullable `limit_requests_per_minute`, `limit_tokens_per_minute`, `limit_tokens_per_day` (DTO `limits`, `src/dto/limits.ts`, `src/limits.ts`; bounds 1 to 10^7 / 10^9 / 10^12). `PATCH /organisations/:orgId` accepts `limits` (partial; null clears one; `{}` is rejected), `POST /organisations/:orgId/api-keys` accepts optional `limits`, `PATCH /organisations/:orgId/api-keys/:keyId` changes them; each records a config change so the gateway picks it up. Benchmarks (`routes/benchmarks.ts`): `GET/POST /organisations/:orgId/pools/:poolId/benchmarks`, `DELETE .../:benchmarkId` (admins create and delete, members read; the pool must serve a model, at least one node online, no other benchmark running in the last 5 minutes; the newest 10 are kept); the status is derived from the per-node results, which the gateways fill in. Migration `0007` adds the limit columns, `node_status.gateway_id` / `gateway_keys`, `gateway_instances`, `benchmarks` and `benchmark_results` (all additive). `gateway_instances`, `node_status` and the benchmark results are written by the gateway only (benchmark rows are created by the control plane and completed by the gateway).
- **More device overrides and device self-info (built)**: `nodes.keep_screen_on` and `nodes.enable_mtp` (nullable booleans, migrations `0008` and `0009`) are settable through `PATCH /organisations/:orgId/nodes/:nodeId` (`keepScreenOn`, `enableMtp`; null = the device decides) and reach the device through `NodeConfig`. The sealed enrollment response now carries `orgName` and `poolName`, and `GET /api/node/me` (device-authenticated, so approved devices only) returns the device's name, organisation (name, slug), pool and approval, which the node app shows.
