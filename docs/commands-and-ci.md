# Commands, CI/CD and release

Summary in [CLAUDE.md](../CLAUDE.md).

- Helm chart: `helm lint chart --strict [-f chart/values-stg.yaml]` and `helm template` with the same flags. Local dev install (`--wait` is required so the ClusterIssuer hooks run after the cert-manager webhook is ready): `helm upgrade -i --wait --timeout 5m --create-namespace -n splitcortex -f chart/values-local.yaml splitcortex chart`.

- Tilt: `tilt up` at the repo root uses the root `Tiltfile` (k3s context `default`, Docker registry `localhost:5000` mirrored in k3s `registries.yaml`). It installs the infra chart as a `chart` local_resource via `helm upgrade -i --wait` (not tilt's `helm()`, because of the ClusterIssuer hooks) with the app workloads disabled (`--set ui.enabled=false --set controlPlane.enabled=false`). Each service has a `docker_build` plus `k8s_yaml(local('helm template ... --show-only templates/<svc>-*.yaml'))` so Tilt owns its workload and swaps in the built image; the `ui`, `control-plane` (plus its `control-plane-migrate` Job) and `gateway` services are wired up (`--set gateway.enabled=false` on the infra install; the gateway's dev image runs `cargo watch`, so its first build in the container takes a few minutes).

- CI/CD for images: reusable template `.github/workflows/docker-service.yaml` (`workflow_call`: `service`, `context`, `dockerfile`). It builds each architecture **natively in parallel** (linux/amd64 on `ubuntu-latest`, linux/arm64 on `ubuntu-24.04-arm`; no QEMU), pushes each image by digest to `ghcr.io/<owner>/splitcortex-<service>`, uploads the digests as artifacts, and a `merge` job creates the multi-arch manifest with the tags (`docker buildx imagetools create`). GHA cache scope is per service and platform. PRs build only (no login, push or merge). Tags: `vX.Y.Z` gives `X.Y.Z` and `X.Y` (no `v`, matches the chart `appVersion`), branch pushes and manual runs give `<branch>` and `sha-<short>`. Each service has a thin caller workflow (`ui.yaml`: PR, push to main with path filter, manual, and `workflow_call`; no tag trigger) and a new service adds one.
- **Release strategy (decided)**: two independent tag streams, tags created by hand (no release-please), no rc tags, and **the same build is promoted** (stg to prd, nothing is rebuilt).
  - **Server: `vX.Y.Z`** (lockstep for chart, ui, control-plane and gateway). `.github/workflows/release.yaml` is the only entry point (tag filter `v[0-9]+.[0-9]+.[0-9]+`). It calls `chart.yaml` (validate, package, push OCI) and every service workflow in parallel, creates the GitHub release (generated notes, marked latest), then `deploy.yaml` for `stg` once all succeed (add a job per new service and list it in `github-release`'s and `deploy-stg`'s `needs`). `chart.yaml` has `workflow_call` and no tag trigger. **Chart version, `appVersion` and image tags are all `X.Y.Z`** (the tag without `v`). prd is promoted manually with `deploy.yaml` using the same version.
  - **Mobile app: `node-vX.Y.Z`**, its own stream because devices update on their own schedule and server releases that do not touch the app must not produce an APK. `.github/workflows/node-release.yaml` is its entry point (calls `node.yaml`, then creates a GitHub release named after the tag, not marked latest, with `splitcortex-node-vX.Y.Z.apk`). The app version and Android `versionCode` come from the tag. Nodes must stay compatible with the server across versions: the node protocol is versioned and the gateway supports the current and previous protocol version (minimum supported app version enforced at connect; not built yet).
  - DB migrations must be expand/contract (additive first, drop later), because `helm --atomic` rolls the app back but not the schema.
- Deploy: `.github/workflows/deploy.yaml` (`workflow_call` and `workflow_dispatch`, inputs `environment` stg/prd and `version`) checks out the tag, substitutes `LETSENCRYPT_EMAIL` into `values-<env>.yaml` and runs `helm upgrade -i --wait --atomic` from `oci://ghcr.io/<owner>/charts/splitcortex`. It runs in the GitHub environment of the same name, which holds the secrets `KUBECONFIG` (plain or base64), `LETSENCRYPT_EMAIL` and `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`; add required reviewers to `prd` for a manual gate. Run it manually to redeploy or roll back; prd is manual only. The cluster must be reachable from GitHub-hosted runners, and GHCR packages must be public or the cluster needs an imagePullSecret (not wired in the chart yet).
- CI/CD for the chart: `.github/workflows/chart.yaml` lints (`--strict`), renders and kubeconform-validates the chart for each of dev/stg/prd on PRs and pushes to `main`. Pushing a tag `vX.Y.Z` packages the chart and pushes it to `oci://ghcr.io/<owner>/charts`. Chart dependencies (`~/.cache/helm`, `chart/charts`) and the kubeconform binary are cached with `actions/cache`, keyed on `Chart.yaml`/`Chart.lock`. Keep action versions on the latest major.

- Web UI (in `src/ui`): `pnpm install`, `pnpm dev` (Vite on :5173; open it as `http://app.splitcortex.127.0.0.1.nip.io:5173` so the Dex URL and redirect URI match the registered client), `pnpm build` (`tsc -b && vite build`), `pnpm typecheck`, `pnpm test` (Vitest run once) / `pnpm test:watch`, `pnpm format` (Prettier write) / `pnpm format:check`. Formatting is **Prettier**, configured in the repo-root `.prettierrc` (single quotes, semicolons, width 100, trailing commas) with `.prettierignore`, plus a root `.editorconfig` (UTF-8, LF, 2 spaces, final newline). Run `pnpm format` before committing UI changes.

- Control plane (in `src/control-plane`, own pnpm project and lockfile like the UI, Docker context `src/control-plane`): `pnpm install`, `pnpm dev` (tsx watch, needs `DATABASE_URL` and `OIDC_ISSUER`), `pnpm test`, `pnpm typecheck`, `pnpm build` (tsup), `pnpm db:generate` (new migration from schema changes, no DB needed), `pnpm db:migrate`, `pnpm format`. CI: `.github/workflows/control-plane.yaml` (listed in `release.yaml`).

- Gateway (in `src/gateway`, Rust, Docker context `src/gateway`; the node protocol proto lives in `src/gateway/proto`): `cargo build`, `cargo test`, `cargo fmt` (`rustfmt.toml`, width 120), `cargo run -- keygen` (new identity key pair), `cargo run` (needs `DATABASE_URL` and `GATEWAY_PRIVATE_KEY`). CI: `.github/workflows/gateway.yaml` (image only; listed in `release.yaml`; the production Dockerfile does not run `cargo test`, run it locally).

- Node app (in `src/node`): `pnpm install`, `pnpm typecheck`, `pnpm test`, `pnpm format` / `pnpm format:check`, `pnpm exec expo export --platform android` (bundle check without a device), `pnpm exec expo prebuild` then `pnpm exec expo run:android` / `run:ios` (local dev build; no EAS, no Expo Go). Add Expo packages with `pnpm exec expo install <pkg>`. `pnpm gen:proto` regenerates `src/protocol/gen` from the gateway's proto (needs `protoc`; commit the result).

CI for the node app: `.github/workflows/node.yaml` (PR/push with path filter, manual). Job `verify` runs typecheck, format check, Jest and an Android `expo export`; job `android` runs `expo prebuild` + `./gradlew assembleDebug` and uploads the debug APK as an artifact (14 days). No image, no deploy; `node-release.yaml` calls it on a `node-vX.Y.Z` tag (`node.yaml` has no tag trigger of its own) and attaches the APK, named `splitcortex-node-vX.Y.Z.apk`, to the GitHub release of that tag (created with generated notes if missing). On a tag it builds a **signed release APK** (`assembleRelease`): the keystore comes from the repository secrets `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` (create them with `src/node/scripts/create-keystore.sh [--upload]`; **back up the keystore, losing it means installed apps can never be updated; never commit it**), read through env vars by the local config plugin `plugins/withReleaseSigning.js` (without them a release build falls back to the debug key, e.g. locally). The version follows the tag: CI sets `APP_VERSION` (tag without `node-v`) and `app.config.ts` uses it as `version` and derives the Android `versionCode` (X*10000+Y*100+Z, so minor and patch must stay <= 99). Non-tag builds are debug APKs named after the commit. iOS is not built in CI (macOS runners and signing, later).

Other commands TBD as code lands.
- Gateway scaling and key rotation (chart values, see [docs/gateway.md](gateway.md)): `--set gateway.replicas=3` runs several instances. Rotating the gateway identity key is one `helm upgrade` per stage: `--set gateway.rotation.stage=prepare`, then `kubectl exec deploy/gateway -- gateway rotation-status` until it says promoting is safe, then `--set gateway.rotation.stage=promote`, then upgrade once more with the stage empty. Each stage restarts the gateways and the control plane.
