# Enrollment and node identity

Protocol, decisions and implementation notes. Summary and hard rules in [CLAUDE.md](../CLAUDE.md).

- **Node identity**: each node generates its own public/private key pair on the device. The private key never leaves the device (use the platform secure keystore where possible). On enrollment the node registers its public key with the platform; the gateway authenticates the node by proof of possession of the matching private key (challenge-response signed during or right after the TLS handshake). Identity comes from the registered key, never from messages on the stream.
- **Server identity**: the server has its own key pair. Nodes learn and trust the server's public key (pin it at enrollment) so they can verify the gateway independently of the TLS CA chain.
- **Enrollment** (initiated from the web app, completed on the device):
  - An admin picks a pool in the web app, which creates an enrollment record (org, pool, expiry ~10 min, single-use, attempt-limited) and shows a **short code** formatted `XXXX-XXXXXX` (Crockford base32, no ambiguous characters). The same code is also shown as a QR for devices with a working camera; the QR is only a convenience and carries the enrollment (BFF) URL plus the same code. **Every device must be able to enroll by typing the code** (no camera required).
  - The first part (4 chars) is a lookup id, unique among all active enrollments across organisations (unique index; not reused until expired). The second part (6 chars) is the secret. Store only a verifier/hash of the secret server-side. The code reveals nothing about org or pool before success.
  - The mobile app takes the code and an **enrollment URL (the control plane / BFF), which has a default and is user-editable** (self-hosted or LAN deployments). The node talks to the BFF, never to the gateway, during enrollment; the PAKE rounds run over plain HTTPS request/response, with in-progress PAKE state kept in the database (or another shared store) so any BFF instance can serve any round.
  - Device keys are **never derived from the code**: the device generates its own non-exportable key pair in the secure keystore. The code only authorizes registering that public key.
  - Because the code is short, use a **password-authenticated key exchange (PAKE; CPace or SPAKE2)** keyed by the secret part, so the code authenticates both sides and cannot be attacked offline. Inside the PAKE-protected channel the BFF sends the **gateway's** public key and the gateway wss URL (the device pins the key) and the device sends its public key and device info. The BFF therefore needs to know the gateway's public key (from configuration or the shared store). This is what lets a short code replace a long pinned-key QR. A fake BFF at an edited URL learns nothing from the exchange.
  - Online guessing is bounded: a few attempts per enrollment, then it is invalidated, plus per-IP rate limits. The secret is single-use and consumed in the same transaction that registers the device.
  - Optional per-pool **admin approval**: the device appears as pending in the web app, showing a short fingerprint of its public key for the admin to compare, and is only active once approved.
  - After enrollment the code is dead; each connection authenticates with the signed challenge. Revoking a node means deleting its registered public key.
- **PAKE spike (2026-11-15)**: CPace (ristretto255/SHA-512) via `@cipherman/pake-js` (pure JS on `@noble/curves`, one dependency, no WASM, so it can run on Hermes; passes the draft-20 test vectors per its README; single maintainer, pre-1.0, **not independently audited**). A Node handshake works (same code gives the same ISK, a wrong code diverges). Not yet run on Hermes (needs `crypto.getRandomValues`, e.g. from `expo-crypto`). `cpace-ts` was rejected (needs WebAssembly, which Hermes lacks). Tentative choice: `@cipherman/pake-js`, with the fallback below kept as the safety net.
- **Enrollment implementation (decided, built)**:
  - Control plane: table `enrollments` (lookup id unique, secret, `expires_at` 10 min, `attempts`/`max_attempts` 3, PAKE session state `session_sid`/`session_isk`), `routes/enrollment.ts`, crypto in `enrollment/crypto.ts`. Admin routes (admin/owner): `POST/GET /organisations/:orgId/pools/:poolId/enrollments` (the code is returned **only** by the create call), `DELETE /organisations/:orgId/enrollments/:id`. Device routes (unauthenticated, per-IP limited, all failures are the same `404`): `POST /api/enroll/start` and `POST /api/enroll/complete`. Expired rows are purged when a new code is created. `trustProxy` is on (behind the ingress) so the IP limiter sees the client.
  - Protocol: **CPace ristretto255/SHA-512** (`@cipherman/pake-js`; PRS = `splitcortex-enroll-v1:<6-char secret>`, CI = `splitcortex-enroll-v1`, device = initiator, the device picks the 16-byte `sid`). Round 1 (`start`: lookup id, sid, share) consumes one of the 3 attempts atomically and stores the derived ISK; round 2 (`complete`) takes the session (one complete per start) and carries the device request **sealed** (ChaCha20-Poly1305, key = HKDF-SHA256(ISK, salt = sid, info `splitcortex-enroll-v1 request|response`), wire format `nonce(12)||ct||tag`). Inside: Ed25519 public key (raw 32 bytes, base64url), a **proof-of-possession signature** over `"splitcortex-enroll-v1" || sid`, and device info. The sealed response returns node id, fingerprint, approval state and the gateway `{publicKey, url}` (from `GATEWAY_PUBLIC_KEY`/`GATEWAY_WSS_URL`, chart `controlPlane.gateway.*`; `null` until the gateway exists). The device accepts the server only if the response opens (mutual authentication) and computes the fingerprint itself. A wrong secret decrypts to nothing, so it looks like any other invalid code; after the attempts are used the row is deleted.
  - Fingerprint: SHA-256 of the raw public key, first 60 bits as Crockford base32 `XXXX-XXXX-XXXX` (shown in the node view and on the phone). The same shared test vectors are asserted on both sides.
  - Deviation from the earlier design, on purpose: CPace is a balanced PAKE, so the server stores the 6-char secret itself (not a hash) for the code's ≤10 minute life, and deletes the row on success, expiry or exhaustion. An augmented PAKE would not help: 30 bits of secret fall to offline guessing either way. Another accepted limit: anyone who can reach the endpoint can burn a code's 3 attempts by guessing its 4-char lookup id (the per-IP limit slows it; the admin just makes a new code).
  - Pool approval: `pools.require_approval` makes the new node `approved = false` (pending) until an admin approves it; otherwise it is active at once. A device key that is already registered gets `409`. A `node` config change is recorded so the gateway learns the node.
  - Phone: `src/node/src/enrollment/` (`crypto.ts` is the byte-compatible device half, verified against the server in a throwaway cross test; `client.ts`, `identity.ts`, `store.ts`). The key pair is generated on first use with `@noble/curves` and kept in `expo-secure-store` (Android Keystore-backed encryption). **It is not a hardware-resident non-exportable key** (Ed25519 is not available through the Expo keystore APIs); a native module could harden this later. `src/polyfills.ts` supplies `crypto.getRandomValues` from `expo-crypto` because pake-js and noble need it. The `.js` noble/pake packages are ESM-only, so Jest's `transformIgnorePatterns` in `package.json` lists `@noble|@cipherman`. The Android bundle compiles to Hermes bytecode (`expo export`), but **the full flow has not been run on a physical device yet**.
- Open decisions: confirm the PAKE library on a device (the bundle builds, no device run yet) (if unusable, fall back to TLS with CA validation plus mandatory admin approval, and document the weaker first-contact trust), bulk code generation for many devices, server key rotation, the gateway challenge-response and key pinning on connect (not built), and whether the key pair is used only for authentication or also to sign messages and model manifests.
