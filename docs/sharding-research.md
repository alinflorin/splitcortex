# Multi-device sharding (research)

Open research, nothing of it is built. Summary in the README roadmap.

Models that do not fit on a single device cannot be served today. Sharding over the internet is not viable (every token crosses every stage, each hop adds a network round trip through the gateway, and any dropped phone kills the request), and LiteRT-LM's public API has no layer-range execution or activation export. The plan is a **local cluster mode**: an opt-in group of devices on the same LAN or switch (a rack of phones or Pis, sub-millisecond RTT) serving one model as a pipeline of layer-range stages, presented to the gateway as a single logical node. It stays on Google's runtime (no second engine): per-stage model conversion, then a custom decode loop (KV cache, sampling) directly on LiteRT, below LiteRT-LM's engine API (or a LiteRT-LM fork), plus direct node-to-node links inside the site (the gateway link stays outbound). Findings so far (from reading the LiteRT-LM sources, not yet confirmed by running anything): the public `Engine`/`Session` API has no layer-range or hidden-state hooks, but the internal `LlmExecutor` interface is a plausible seam. The LiteRT compiled-model executor keeps the KV cache as explicit input/output tensor buffers of the graph signatures, and prefill and decode already run as separate signatures (prefill can take embeddings), so a pipeline stage looks like a new executor over per-stage graphs. Inspecting a real file (Qwen3-0.6B `.litertlm`, via `litert-lm-peek` and the TFLite interpreter) confirmed: one monolithic TFLite graph with separate `prefill_128`/`prefill_1024`/`decode` signatures (tokens, positions and mask in, logits out; embedding lookup and LM head inside the graph), the KV cache as explicit per-layer `kv_cache_k_N`/`kv_cache_v_N` inputs and outputs (56 for 28 layers), weights in a separate section, and tensor names scoped by decoder layer (`Qwen3DecoderLayer_N`). The exporter (`litert-torch export_hf`) wraps the PyTorch model in an exportable module, so a layer-range stage is most likely a PyTorch-level change there rather than flatbuffer surgery (exporter source not yet read, nothing exported yet). Open points: whether the exporter can emit layer-range graphs with hidden-state inputs and outputs, model-specific state (sliding-window caches, per-layer embeddings), and that NPU builds are precompiled and not splittable. **Spike result (offline proof, tiny random Qwen3, 4 layers, fp32):** two stage models (layers 0-1 and 2-3) were exported with the stock `litert-torch export_hf` flow by saving per-stage checkpoints (first stage: final norm and LM head replaced by identity so it outputs hidden states; second stage: `--externalize_embedder` so it takes hidden states as embeddings). Running the stages back to back through the `decode` signatures reproduced the unsplit model's logits exactly (max difference 0 against the unsplit export, 3e-7 against HF eager, 24/24 tokens), each stage holding only its own layers' KV cache, with 256 bytes of hidden state per token handed over (hidden size times 4 bytes; about 4 KB for Qwen3-0.6B). Not yet shown: prefill (the exporter's prefill emits no per-position hidden states, so it needs a small wrapper change), a real-size or quantised model, sliding-window/per-layer-embedding architectures, and execution inside LiteRT-LM's own executor (the test used the plain LiteRT interpreter). Next steps: stage-aware prefill, a real model, then a LiteRT-LM stage executor. Original first step was a time-boxed spike: check what LiteRT exposes (partial graphs, intermediate tensors, KV cache control), convert a small model into two layer-range stages, and run them on two devices on one LAN, measuring per-token latency. Until then, larger models are handled by device capability reporting, per-model minimum requirements and quantisation, not sharding.
