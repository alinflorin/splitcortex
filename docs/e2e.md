# End-to-end tests (`e2e/`)

Summary in [CLAUDE.md](../CLAUDE.md). One pnpm project, one runner (**Playwright Test**), eight projects (the eighth, `perf`, is on demand), all against a **deployed stack** (never mocks). Each suite makes a throwaway org + pool through the control plane API (signing in to Dex headlessly with PKCE, `src/dex.ts`), uses an enrollment code from it and deletes the org at the end.

| Project | What it drives | How |
| --- | --- | --- |
| `platform` | web app: Dex login, org/pool pages, **operator flows** in `ui.spec.ts` (create org, create approval pool, enrollment code + QR, API key secret shown once then revoke, delete pool, audit log page and filters, **audit export** (CSV and JSON downloads), **Add model dialog with the Type radio and the embedding mark on the card**, **bulk enrollment dialog** (bounds, codes shown, unused ones cancelled on close), **the node page's Restart button (disabled while the device is offline)**, metrics page, account deletion refused for a sole owner), deployment smoke (`/version.json`, `/api` 401, Dex discovery, sign-in redirect) | Chromium |
| `web-node` | the web node: served, join form, a browser tab enrolls with a code, a used code is refused | Chromium (one fresh context per device) |
| `api` | the control plane's rules over HTTP, **no node**: enrollment limits (3 guesses, cancelled code, 10 min, codes never listed), input validation (model URL/file, API key scope/expiry/limits), secret returned once, uniqueness, org delete; `audit.spec.ts` (control plane mutations recorded with actor, no secrets, filters, cursor paging, org isolation); `features.spec.ts` (**remote restart** without a node: 409 for an enrolled-but-offline device, 404 for an unknown device/organisation/another tenant; **model `kind`**: default `chat`, `embedding` on from-url and upload, a bad kind is 400; a **benchmark on an embedding pool is 409** (the pool serves a placeholder upload, the kind is checked before whether a node is online); **audit export** CSV (default, header, attachment name) and JSON with the list's filters, bad format 400, foreign org 404; **bulk enrollment** (distinct single-use codes, count 1..50, 404 unknown pool, one `enrollment.create_bulk` audit row); **API key expiry change** `PATCH /api-keys/:id` (set, `null` clears, past or bad date 400, limits kept, revoked key 409). The refusals for plain members (403) cannot be tested: only one login exists, the control plane's own tests cover them); `account.spec.ts` (`/me`, a sole owner cannot delete the account; the success path is **not** run because the shared e2e login would lose its memberships in parallel suites, it is covered by `me.test.ts`) | `fetch` against `/api` |
| `cli` | the real `splitcortex-node` binary: `join` (wrong code, real code, already enrolled), node appears in the control plane, `run` goes online then offline, `leave`, **approval pool** (`approval.spec.ts`: enrolls pending, admin approves) | child processes with `SPLITCORTEX_HOME` in a temp dir |
| `serving` | the gateway and control plane with a **live node** (the node kind is irrelevant; `src/serving-node.ts` starts the CLI, the headless one, and is the only file to change for another): `inference.spec.ts` (the node downloads the pool's model, an OpenAI chat completion in JSON and SSE through the gateway, `/v1/models`, 401/404) and `keys-limits.spec.ts` (revoked key refused, pool-scoped key, 429 in the OpenAI error shape, another org sees nothing, usage per key recorded, **the usage dashboard** shows the same totals and groups by key in the browser). `playground.spec.ts` (the web app's Playground page: a wrong key shows the gateway's error, a pasted key lists the model (**chat models only: an embedding model of the same org is not offered**) and chats with the live node with streamed output and a timing line, all through `/v1` on the app origin, nothing kept after a reload; needs the chart's `gateway.appIngress`, so it fails on a stack deployed before it existed). `embeddings.spec.ts` (**`POST /v1/embeddings` and model kinds**. Part 1, always: next to the chat model the org gets a second pool serving a *placeholder* embedding model (a few bytes, no node can load it), which is enough for `/v1/models` carrying `kind` (`chat`/`embedding`), `400 wrong_model_kind` both ways (chat model on `/v1/embeddings`, embedding model on `/v1/chat/completions`), `404 model_not_found`, `401`, the input/option validation (empty, blank, empty list, 129 inputs, 32001 characters, bad `task`, bad `encoding_format`, `dimensions` 0, all `400 invalid_request`; 128 inputs pass), `503` with no node for the pool, `429` from an org limit. Part 2, **only with `E2E_EMBEDDING_MODEL_URL`**: a real embedding model on a CLI node: OpenAI list shape and usage, unit-length vectors, batch order, similar texts closer than unrelated ones, `dimensions` truncation + renormalisation (and more than the model has = 400), `base64` equals the little-endian float32 bytes, `task` changes the vector, metering); `restart.spec.ts` (**remote restart of a live node**: `POST .../restart` answers 202, the node's `live.connectedSince` moves and it serves a chat request again, the `node.restart` audit row, the node page's Restart button with its confirm dialog and the "Restart sent." toast, then a stopped node: 409 and a disabled button); `metrics.spec.ts` (traffic and node telemetry reach `GET /metrics` through the gateway's minute batches, **the gateway-measured per-node `requests`, `failures` and `measuredTokensPerSec`**, pool/node filters, 7-day cap, org isolation, charts in the web app; slow, waits up to 3 min for the batch). `lifecycle.spec.ts` (also the gateway's audit rows: node connected/disconnected, limit exceeded; live telemetry, benchmark, stop/restart, org-wide limit, node revoke). Each spec starts its own node | HTTP against the gateway + control plane API |
| `perf` | **load** on the gateway and control plane with **simulated nodes** (`src/perf/fake-node.ts`: enrolls through the real CPace exchange, speaks the real wss + protobuf handshake, answers with N pieces on a timer, never downloads the model, so the numbers are platform overhead, not model speed). `embeddings.spec.ts` (`/v1/embeddings` against simulated nodes that answer `EmbeddingRequest` with deterministic vectors, `fakeEmbedding` in `fake-node.ts`: latency and req/s per concurrency step, one vector per input in order with the node's dimension, `dimensions`/`task` reach the node, usage tokens-in equal what the nodes embedded; extra knob `PERF_EMBED_INPUTS`) and `restart.spec.ts` (every simulated node is restarted through the API, closes and reconnects with a new `connectedSince`, the pool serves again; knob `PERF_RESTART_NODES`). `streaming.spec.ts`: time to first token, inter-token gaps and req/s as concurrent SSE clients rise (`src/perf/sse-client.ts`, plain `fetch`, no browser), then the **metering check** (the org's usage totals equal what the nodes sent). Results go to `perf-results/*.json` (git-ignored); a file of the same name in `perf-baseline/` (committed, copy a result there to start tracking) makes the run fail on a slowdown above `PERF_TOLERANCE` (default 50%). Run with `pnpm test:perf` (sets `E2E_PERF=1`; a plain `pnpm test` skips it). Knobs: `PERF_NODES`, `PERF_STEPS`, `PERF_REQUESTS`, `PERF_TOKENS`. **Point it at a local or dedicated stack, not shared staging** (load, per-IP enrollment limits). In `e2e.yaml` only on demand: `suites = perf` runs it alone, `perf = true` with `suites = all` adds it **after** the functional jobs (`needs`, and only when none failed; never in parallel, the load would slow them), the nightly run never has it; `perf_nodes`/`perf_steps` inputs; results uploaded as the `e2e-perf-results` artifact (90 days). | `fetch` + `WebSocket` (Node), no browser |
| `desktop` | the real Tauri app: join form, wrong code, enroll | `tauri-driver` + WebdriverIO `remote()` (Playwright is only the runner). Linux/Windows; macOS has no driver |
| `mobile` | the real Android app: wrong code, enroll | Maestro flows in `maestro/` on an emulator or USB device |

**Embedding test model (optional)**: a real embedding needs a `.litertlm` embedding model, which no one can fake. Set **`E2E_EMBEDDING_MODEL_URL`** (a Hugging Face link, for example EmbeddingGemma's `.litertlm`; the control plane mirrors it from there, so it must be reachable without a token) and the *real embeddings* tests of `tests/serving/embeddings.spec.ts` run (a CLI node downloads it from the control plane, loads it into the embedding engine; allow several minutes); without it they are skipped with that message. **Kind tests and the Add model / embedding card checks do not need it**: they use a placeholder upload. The CLI node of the *newest release* must know embeddings (`ModelAssignment.kind`) and `Restart`; with an older build set `E2E_SKIP_RESTART=1` to skip the restart spec.

**Inference test model**: SmolLM2 135M Instruct (`litert-community/SmolLM2-135M-Instruct`, ~143 MB, Apache-2.0, not gated). `src/model.ts` reuses `e2e/.cache/models/` (git-ignored; `E2E_MODEL_DIR` moves it; the workflow caches it) and downloads it from Hugging Face when missing; the suite uploads it to the throwaway org through the control plane's multipart upload, assigns it to the pool, creates an API key and calls `<gateway>/v1/*` (`E2E_GATEWAY_URL`, default the `gateway.` sibling of the app host). Assertions are about structure (status, shape, token counts), never the text.

Not covered: gateway routing on the *measured* speed (needs two nodes of different speed; only the measured numbers themselves are asserted), the web/desktop/mobile nodes serving embeddings or restarting (only the CLI node and the simulated nodes are driven), restart while requests run (grace period), the 409 of a restart for a node whose gateway instance is down.

Not covered yet (perf): reconnect storm, drain under load, multi-gateway forwarding, config propagation latency, 1000+ nodes (the fleet enrolls 5 at a time and may hit the per-IP enrollment limit), the 429 path under load. The simulated node answers `EmbeddingRequest` and `Restart` too (it must follow `node.proto`; `pnpm gen:proto` refreshes its copy). It copies the web node's crypto and handshake (`src/web-node/src/enrollment/crypto.ts`, `protocol/handshake.ts`), so a protocol change must be made there too; its proto copy is `pnpm gen:proto`. The perf suite was written without a running stack and has never been run.

Not covered yet: members and roles (only one login exists), model swap on a live pool, enrollment through the real CPace exchange for other node kinds beyond enrolling, the other node kinds serving.

## Running

`cd e2e && pnpm install`, then **`pnpm dev`**: it asks for the Dex email and password (skipped when `E2E_EMAIL`/`E2E_PASSWORD` are set in the environment or in **`e2e/.env`**; the password is not echoed) and runs Playwright against the **local stack** (Tilt, default `https://app.splitcortex.127.0.0.1.nip.io`; Dex = `dex.` and web node = `web-node.` siblings). `pnpm dev` shows the browser window (`--headed`; `--headless` hides it). Other arguments pass through to Playwright: `pnpm dev --project=cli`, `pnpm dev tests/platform/smoke.spec.ts`. The raw runner is `pnpm test` / `pnpm test:platform|web-node|cli|desktop|mobile` (needs the two variables, from the environment or `e2e/.env`). Other stacks: `E2E_APP_URL` (staging: `https://app.stg.splitcortex.alinflorinciu.qoffice.ro`; `E2E_DEX_URL` / `E2E_WEB_NODE_URL` when the hosts don't follow the `app.` pattern). The workflow sets `E2E_APP_URL` to staging itself. `e2e/.env` is git-ignored (copy `.env.example`; any `E2E_*` variable can go there, the environment wins). Local login: a user from `values-local.yaml`. To test staging set `E2E_APP_URL=https://app.stg.splitcortex.alinflorinciu.qoffice.ro` and the stg user's login (in `.env` or per run). Local TLS: the browser project accepts the throwaway CA on nip.io hosts; Node needs `NODE_EXTRA_CA_CERTS=<root CA pem>` (Secret `root-ca-issuer`, key `ca.crt`), and the CLI/desktop apps need the CA in the OS trust store; mobile needs a debug APK (release builds do not trust user CAs) and `scripts/start-emulator.sh`.

A suite whose binary/device is missing **skips locally and fails in CI**: `E2E_CLI_BIN` (default: the **newest published cli-node release**, which `src/global-setup.ts` installs with `src/cli-node/install.sh` into `e2e/.cache/cli-node` on every run of the `cli`, `serving` or `perf` projects, reusing the earlier download when offline; in CI the workflow installs it the same way; set `E2E_CLI_BIN` to test a local `cargo build --release` or a pinned build instead), `E2E_DESKTOP_BIN` (default `src/desktop-node/src-tauri/target/release/splitcortex-desktop-node`; also `tauri-driver` on PATH via `cargo install tauri-driver --locked`, `webkit2gtk-driver` and a display on Linux), `E2E_MOBILE_APK` (optional; else the app is already installed; `adb` device + `maestro` needed; local emulator: `scripts/start-emulator.sh`). The desktop suite runs the app with `XDG_*` dirs in a temp dir so a real enrollment is untouched.

## The e2e login (repository secrets, provisioned by the stg deploy)

**Repository** secrets **`E2E_EMAIL`** (an email address) and **`E2E_PASSWORD`** (plain; the tests need it), used by both `e2e.yaml` and `deploy.yaml` (so no environment is needed for the e2e workflow). `deploy.yaml` (stg only) bcrypt-hashes the password with `htpasswd` into `E2E_PASSWORD_HASH` and `envsubst`s it and the email into `values-stg.yaml`'s `dex.config.staticPasswords` (user `e2e`); the deploy fails if a secret is missing. The user exists on stg after the next stg deploy; changing the password = change the secret and redeploy stg. Do not also set them as environment secrets: those would shadow the repository ones. prd has no such user. Locally the suites need `E2E_EMAIL`/`E2E_PASSWORD` (`e2e/.env` or the environment; against staging the same values as the secrets; against the local stack any user of `values-local.yaml`).

## Workflow

`.github/workflows/e2e.yaml`: nightly (03:00 UTC) and manual; jobs `platform`, `web-node`, `cli`, `desktop`, `mobile` run in parallel (no GitHub environment; they use the repository secrets). Manual inputs: `app_url` (default staging; `dex_url`/`web_node_url` if not derivable; another stack must accept the same login), per-stream versions, `suites`. The node suites test the **newest released builds** (CLI via `install.sh`, desktop `.deb`, mobile APK) unless a version is given. Mobile uses `reactivecircus/android-emulator-runner` (API 34, KVM) and the newest Maestro release (unpinned).

**Caches** (`actions/cache`): the pnpm store, Playwright's browsers (key = `e2e/pnpm-lock.yaml`; apt libraries are still installed each run with `install-deps`), `tauri-driver` (so the Rust toolchain and `cargo install` only run on a miss; bump the `v1` in the key to rebuild), Maestro (key = its release tag) and the Android emulator's AVD with a booted snapshot (key `avd-<api>-<arch>-<target>` built from the mobile job's `ANDROID_*` env, so changing the image starts a fresh cache; the image is the lightweight ATD `google_atd`, API 34, x86_64; created by the first run; the emulator then starts with `-no-snapshot-save`). The emulator's **system image** is cached too (key `sdk-image-<api>-<arch>-<target>`; the runner's SDK folder is root-owned, so the job first `chown`s `$ANDROID_HOME/system-images` to the runner user, which is the only SDK folder restored into; the preinstalled emulator and platform tools stay as they are). The AVD and image caches use `cache/restore` + `cache/save` (the AVD right after it is created, the image after the tests with `always()`), because a plain `actions/cache` only saves when the whole job passes, so a failing test run would never populate it. Not cached: apt packages (`webkit2gtk-driver`, `xvfb`, the .deb's dependencies) and the downloaded release assets (CLI archive, `.deb`, APK). Caches belong to the branch that created them and are evicted after 7 days unused, which the nightly run prevents.

## Unverified

Expect a first round of fixes.
