# CLAUDE.md

Guidance for Claude Code when working in this repository. Rules and decisions that always apply are here; the long implementation detail lives in [docs/](docs/) and must be read before changing the area it covers (and kept up to date).

## Project

SplitCortex is a SaaS platform for reusing mobile compute devices (phones, Raspberry Pis, etc.) as inference serving nodes. See [README.md](README.md) for the product overview.

## Tech stack

**Frontend (`src/ui`, pnpm)**: Vite, React, TypeScript (strict, no `any`), Fluent UI React (the only component library), react-hook-form + zod (`@hookform/resolvers/zod`; zod messages are i18n keys), React Router, react-i18next (en + ro), TanStack Query, Vitest + React Testing Library, Dex OIDC via `react-oidc-context`. **Cards, never tables or data grids.** Navigation lives in the sidebar. **No CDNs, ever** (fonts, scripts, icons): fonts are self-hosted. Light, airy design (hairline borders, no heavy shadows). Details: [docs/ui.md](docs/ui.md).

**Endpoint app (`src/mobile-node`, own pnpm project)**: React Native + Expo (SDK 58, Expo Router, `expo-dev-client`), TypeScript. Fluent UI React is DOM-only, so it reuses only the Fluent design tokens with its own thin components; do not add another component library. Jest tests. Local dev builds only: **no EAS, no Expo Go**. The engine (LiteRT-LM) sits behind an interface; the app must keep its TLS connection to the gateway alive while serving. Enrollment, the gateway connection (pinned-key handshake, reconnect), live model download/replace, the engine adapter (`react-native-litert-lm`, third party, not run on a device), the Logs screen, restart and the start settings are built; the Android background service (foreground service + headless JS, boot start) and native cpu/memory/battery telemetry are built in a local Expo module (compiled, not run on a device). **An iOS node is foreground-only** (iOS suspends background apps; nothing built or run on iOS yet); the identity key stays Ed25519 in `expo-secure-store` (no hardware keys). Compute backend (cpu/gpu), context window, multi-token prediction and keep-the-screen-on: admin override per device (web, `NodeConfig`) > the app's setting > automatic (measured fastest / RAM based). Details: [docs/node-app.md](docs/node-app.md).

**Web node (`src/web-node`, own pnpm project)**: a static web app, same stack as the UI (Vite, React, Fluent, react-hook-form + zod, react-i18next, Vitest, no CDNs, cards), served at `web-node.<domain>`: a browser tab that enrolls and serves like a phone node (same enrollment, protobuf-over-wss gateway connection, signed model download from the control plane into OPFS, the engine is Google's LiteRT-LM JS/WASM/WebGPU API behind the `Engine` interface). It behaves like the other nodes: the code comes from **Add device** and is typed in (the web app does **not** open it with a code; the page still accepts `#code=` but nothing links to it). The web app's `AppDownloads` section (home and pool screens) presents mobile, desktop, command line and web node: release links `releases?q=mobile-node&expanded=true` / `q=desktop-node` / `q=cli-node`, store buttons inert, install one-liners with copy buttons, web node open (new tab) and share buttons. Its ingress host also routes `/api` to the control plane (same origin, **no CORS**). Foreground only, not run in a real browser against a real model yet. Details: [docs/web-node.md](docs/web-node.md).

**Desktop node (`src/desktop-node`, own pnpm project)**: a Tauri 2 app (Linux x64/arm64, macOS arm64, Windows x64) that enrolls and serves like a phone node. Web side = the web node's stack and code ported (Vite, React, Fluent, react-hook-form + zod, react-i18next, Vitest, no CDNs, cards, same look); native side in Rust (`src-tauri`): the engine is Google's **official LiteRT-LM C API loaded at run time with `libloading`** (no Rust crate exists; the per-platform library is fetched by `scripts/fetch-litert.mjs` with a pinned SHA-256, **there is none for macOS x64 so that target is not built**), model files and the device key on disk (key file mode 0600), control plane calls through Tauri's HTTP client (**no CORS**), tray with close-to-tray, sleep prevention, autostart. Releases: tag **`desktop-node-vX.Y.Z`** (own stream; installers + signed updater bundles on a GitHub release that is **not** "latest"; the updater reads `latest.json` from the rolling release `desktop-node-updater`; secrets `DESKTOP_NODE_SIGNING_PRIVATE_KEY[_PASSWORD]`); **no release-cache workflow**. Engine verified only up to "the real library loads and every function resolves", never run on a real model. Details: [docs/desktop-node.md](docs/desktop-node.md).

**CLI node (`src/cli-node`, Rust only, no pnpm)**: the headless sibling of the desktop node for Linux x64/arm64, macOS arm64 and Windows x64: enrolls (`join`), serves (`run`), runs as a background service (`service install`: systemd user unit / launchd agent / scheduled task) and updates itself (`update`). **Kept completely separate from the desktop node** (no shared crate): the engine binding (`engine/ffi.rs`, same LiteRT-LM C API loaded with `libloading`, library fetched by `scripts/fetch-litert.py` with the same pinned SHA-256, none for macOS x64) is a copy, and enrollment crypto (CPace ristretto255, checked byte for byte against `@cipherman/pake-js`), the gateway handshake, the model manager and the runtime are Rust ports of the desktop node's TypeScript, so **a fix in one must be made in the other**. The protobuf is generated from `src/gateway/proto` by `build.rs` (`protox` + `prost`, no copy). Releases: tag **`cli-node-vX.Y.Z`** (own stream, not "latest"; archives `splitcortex-node-<target>.tar.gz|zip` + `.sha256` with the library next to the binary; no secrets, no release-cache workflow). Installed by `src/cli-node/install.sh` / `install.ps1`, **served from GitHub raw** (`raw.githubusercontent.com/alinflorin/splitcortex/main/src/cli-node/`), shown with copy buttons in the web app's *Command line* card. Not verified: enrollment against a running control plane, a real gateway session, generation on a real model, `install.ps1`. Details: [docs/cli-node.md](docs/cli-node.md).

**Backend**: two deployables.

- **Control plane: TypeScript + Fastify.** Accounts, orgs, memberships, pools, keys, config, dashboards, enrollment, benchmarks. Shares zod schemas and inferred types with the frontend through a workspace package (e.g. `packages/shared`); validate every request/response at the Fastify edge with them (e.g. `fastify-type-provider-zod`).
- **Gateway: Rust** (`src/gateway`, built: node WebSocket + OpenAI edge + config cache + metering + per-key/org rate limits (429) + connection resume + graceful drain on shutdown (running requests finish, up to 1 h) + several instances (forwarding over an internal port, no extra software) + benchmarks + key rotation, see [docs/gateway.md](docs/gateway.md)), for performance. It terminates the OpenAI-format HTTP/SSE edge and the node WebSocket (wss) connections, and does auth, limit checks, metering, load balancing and model management on the hot path. Suggested stack (not yet fixed): tokio, axum, tokio-tungstenite or axum WebSocket, rustls, prost for protobuf. It is a long-running process or container; do not use serverless functions anywhere in the backend.
- **The zod schemas are not shared with the gateway.** The cross-language contracts are: (1) the protobuf node protocol (single source, generate TS and Rust code from it), (2) the OpenAI wire format at the gateway edge, (3) the shared data store / internal API between control plane and gateway. Do not duplicate business rules in both languages: the control plane owns all writes to accounts, orgs, pools, keys, limits, enrollment and node registration; the gateway only reads that state (cached) and writes usage records. **Enrollment never touches the gateway**: nodes enroll against the control plane (Fastify/BFF) over HTTPS; the gateway only sees nodes that are already registered.
- **Gateway config cache (decided)**: node records, pools, models, API key hashes and limits live in gateway memory, fed by a `config_changes` table plus Postgres `LISTEN/NOTIFY` (re-fetch the row, never apply diffs; missing row = delete; full resync on a gap). **No Redis.** Only hashes of API keys are stored or cached. Usage counters are flushed to `usage_records` in additive batches (fail closed with `503` when the buffer is full or stale). Prometheus/OpenTelemetry are deferred. Full design: [docs/gateway.md](docs/gateway.md).
- **Control plane (`src/control-plane`)**: Fastify 5 + `fastify-type-provider-zod`, Postgres via Drizzle (plain SQL migrations committed in `drizzle/`, never hand-edit applied ones; expand/contract only), DTOs in `src/dto` (no shared package; the UI copies what it needs by hand), Dex JWT auth (no users table), public routes under `/api`, tests on PGlite. Organisations, memberships, pools, nodes, models (object storage via Garage, uploads streamed through the control plane; **nodes download their pool's models from the control plane directly**, `GET /api/node/models[/:id/file]`, authenticated by a per-request Ed25519 signature of the enrolled device key; a daily CronJob `control-plane-sweep` aborts abandoned multipart uploads), API keys, usage reads and enrollment are built; benchmarks are built (the gateways run them) and so are rate limits. The gateway writes only `usage_records`/`node_status`/`gateway_instances`/benchmark results. Full detail: [docs/control-plane.md](docs/control-plane.md).

## Domain model

- **User**: registers an account.
- **Organisation**: created by users; has members with roles (membership management).
- **Pool**: an inference pool owned by an organisation; contains device nodes and serves a set of models.
- **Node / device**: a phone, RPi, etc. registered to a pool. Runs LiteRT-LM.
- **API key**: belongs to an organisation, scoped to the whole organisation or to chosen pools; used by clients to call the gateway.
- **Model**: owned by an organisation (a `.litertlm` file in object storage, added from a Hugging Face URL or uploaded), assigned to pools. **A pool serves exactly one model** (assigning another replaces it); every node of the pool holds it (serving type `replicated`).
- **Usage record**: token usage per key / pool / org, used for limits and dashboards.

## Architecture rules

- The platform has a **control plane** (Fastify: accounts, orgs, pools, keys, config, dashboards) and an **API gateway** (Rust: auth, limits, metering, load balancing, model management). They are separate services sharing a data store; the gateway never owns configuration data.
- Nodes connect **outbound** to the gateway over a persistent **WebSocket** connection secured with **TLS** (wss), carrying **protobuf** messages. Multiplexing is application-level: every message carries a request id, with credit-based backpressure, ping/pong keepalives and reconnect with resume. The protobuf schema is the versioned node protocol contract; keep it transport-independent. **The proto lives in `src/gateway/proto`** (so the gateway's Docker build context stays its own folder; no multi-folder contexts); the node apps (phone, web and desktop node) each commit a generated TS copy (`pnpm gen:proto`); the CLI node generates Rust from it at build time. There is **no message broker** for now: the gateway keeps an in-memory registry of connected nodes per pool and relays requests and streamed tokens over the node's stream. Keep the node connection behind a transport interface (e.g. `NodeChannel`) so multi-gateway scaling (shared registry, gateway-to-gateway forwarding, or NATS) can be added later. Never design anything that requires inbound connectivity to a device.
- The gateway exposes the **OpenAI API format** (e.g. `/v1/chat/completions`, `/v1/models`, streaming via SSE) so existing OpenAI clients and SDKs work by changing only the base URL and API key. Keep this wire format at the gateway edge; translate to the internal node protocol behind it.
- The gateway has two distinct legs; do not conflate them. The OpenAI handler and the node registry/sockets must live in the same process (or instance group), so the client-facing endpoint must not be split out into a separate service or function:

  ```
  client ──HTTPS + SSE (OpenAI format)──▶ gateway ──WebSocket + protobuf (wss)──▶ node
          client-initiated, per request                node-initiated, long-lived, multiplexed
  ```

- The web app includes a **performance measurement** feature (e.g. benchmarking nodes and pools: latency, throughput, tokens/sec). Measurements must be scoped by organisation like all other data, and must not log prompts or completions (benchmark prompts excepted if they are platform-supplied).
- Every inference request must be authenticated by API key, checked against limits, routed to a healthy node in the target pool, and metered (tokens in/out).
- **Routing**: API key hash, then org, limits and target pool, then a node from the in-memory registry keyed by `(org, pool)`; the pool is resolved from the request's `model`. Balancing, failure and key-scope rules: [docs/gateway.md](docs/gateway.md).
- Models are **replicated** per device for now. Keep model placement behind an abstraction so sharding a large model across devices (open research) can be added later without rewriting the gateway.
- **LiteRT-LM** is the only supported engine. Keep the engine behind an interface; do not leak LiteRT-LM specifics into gateway or billing code.
- Tenant isolation is critical: every query, node stream and registry entry must be scoped by organisation.

## Security

- API keys: store only hashes, show the secret once at creation.
- Node authentication must be per-device credentials, revocable individually.
- **Node identity**: each node generates its own public/private key pair on the device. The private key never leaves the device (use the platform secure keystore where possible). On enrollment the node registers its public key with the platform; the gateway authenticates the node by proof of possession of the matching private key (mutual challenge-response on connect, built: the node first verifies the gateway's signature against the pinned key, then signs; see [docs/gateway.md](docs/gateway.md)). Identity comes from the registered key, never from messages on the stream.
- **Server identity**: the server has its own key pair. Nodes learn and trust the server's public key (pin it at enrollment) so they can verify the gateway independently of the TLS CA chain.
- **Enrollment**: the admin creates a short code `XXXX-XXXXXX` (10 min, single use, 3 attempts, generic 404 on every failure, per-IP limit) plus a QR; the device always can type it. A CPace PAKE keyed by the secret part authenticates both sides and carries the device's public key (proof of possession) and the gateway's pinned public key and wss URL; device keys are never derived from the code; optional per-pool admin approval. Enrollment never touches the gateway. Protocol, deviations (the server stores the 6-char secret briefly), library caveats and open decisions: [docs/enrollment.md](docs/enrollment.md).
- Validate TLS properly on the node connection; no disabled certificate checks, even in dev shortcuts. The node also verifies the gateway against the pinned server key.
- **Gateway identity key**: created once by a Helm hook Job into two k8s Secrets (private key for the gateway only, public key for the control plane), never rotated by upgrades, never in a committed file; see [docs/gateway.md](docs/gateway.md).
- Do not log prompts, completions, or key material.

- `src/cli-node` is plain Cargo (`cargo fmt`, `cargo clippy --all-targets -- -D warnings`, `cargo test`, `cargo build --release`; `python3 scripts/fetch-litert.py` first so the library-loading test runs).
- Releases: server tags `vX.Y.Z` (lockstep chart/ui/control-plane/gateway, the same build is promoted stg to prd); mobile tags `mobile-node-vX.Y.Z`; desktop tags `desktop-node-vX.Y.Z`; CLI tags `cli-node-vX.Y.Z`. Chart/app versions are the tag without `v`. **Push release tags one at a time** (a separate `git push origin <tag>` each, a few seconds apart): GitHub fires no tag-push workflows when more than 3 tags arrive in one push, so a batch silently starts no releases (this happened with 1.3.0, whose four tags were pushed together).

## Working conventions

- **No resource requests or limits anywhere in the chart** (no `resources:` on our workloads or subcharts); do not add them.

- **Every new deployable project/service must ship with**: (1) a `Dockerfile` in its folder (build context = that folder unless it needs shared packages), run as non-root, with a health endpoint; (2) chart templates named `<svc>-deployment.yaml`, `<svc>-service.yaml`, `<svc>-ingress.yaml` (and others as needed) under a `<svc>:` values block with `enabled` (ingress enabled by default where it is public, per-env host/TLS/issuer overrides in `values-stg.yaml`/`values-prd.yaml`); (3) a Tiltfile entry (`docker_build`, `k8s_yaml` from `helm template --show-only`, `k8s_resource` with `resource_deps=['chart']`) and `--set <svc>.enabled=false` on the chart install; (4) CLAUDE.md and README updates for the above. The UI (`src/ui`) is the reference implementation.
- **Tilt uses a dev image.** Each service has `Dockerfile` (production) and `Dockerfile.dev` (used only by the Tiltfile `docker_build`): the dev one runs the service's hot-reload dev server/watcher on the same container port as production (so the chart's Service, Ingress and probes work unchanged, including a `/healthz` endpoint) and the Tiltfile adds `live_update` (sync sources, `fall_back_on` dependency manifests and config). Dev-only chart overrides (e.g. writable root filesystem) are passed with `--set` in the Tiltfile's `helm template`, never baked into `values.yaml` defaults. UI: `src/ui/Dockerfile.dev` runs Vite on 8080.
- **Image names differ per environment.** Local (Tilt) uses the bare name `splitcortex/<svc>` (the chart default; Tilt substitutes the locally built image). stg/prd override `<svc>.image.repository` in `values-stg.yaml`/`values-prd.yaml` to the GHCR path `ghcr.io/alinflorin/splitcortex-<svc>` (UI: `ghcr.io/alinflorin/splitcortex-ui`); the tag defaults to the chart `appVersion`. Keep the chart default and the `docker_build` name in the Tiltfile identical. CI builds and pushes service images to GHCR (see CI/CD above).

- **Always keep CLAUDE.md and README.md up to date.** Any change to a decision, architecture, security design, stack, commands or layout must update both files in the same change (CLAUDE.md for rules and constraints, README.md for the product-level overview). Do not leave them stale or contradicting each other or the code.
- Prefer small, focused commits. Do not commit unless asked.
- Open research items (multi-device model sharding) belong in the README roadmap, not as speculative code. Decided direction for sharding: only as an opt-in **local cluster mode** (same-LAN nodes acting as one logical node behind `NodeChannel`/the placement abstraction); never sharding across the internet. Engine decision: stay on Google's runtime, so cluster mode is a custom pipeline on LiteRT (below LiteRT-LM's engine API) behind the engine interface, not a second engine such as llama.cpp. Not built; an offline spike already showed a layer-range split through the stock exporter reproduces the unsplit logits exactly in decode (see README roadmap for scope and what is still unproven: prefill, real models, LiteRT-LM executor).
