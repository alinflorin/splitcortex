# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project

SplitCortex is a SaaS platform for reusing mobile compute devices (phones, Raspberry Pis, etc.) as inference serving nodes. See [README.md](README.md) for the product overview.

The repository is currently empty apart from docs. Update the "Commands" and "Layout" sections below as code lands.

**Backend (decided)**: two deployables with different languages.

- **Control plane: TypeScript + Fastify.** Accounts, orgs, memberships, pools, keys, config, dashboards, enrollment, benchmarks. Shares zod schemas and inferred types with the frontend through a workspace package (e.g. `packages/shared`); validate every request/response at the Fastify edge with them (e.g. `fastify-type-provider-zod`).
- **Gateway: Rust**, for performance. It terminates the OpenAI-format HTTP/SSE edge and the node WebSocket (wss) connections, and does auth, limit checks, metering, load balancing and model management on the hot path. Suggested stack (not yet fixed): tokio, axum, tokio-tungstenite or axum WebSocket, rustls, prost for protobuf. It is a long-running process or container; do not use serverless functions anywhere in the backend.
- **The zod schemas are not shared with the gateway.** The cross-language contracts are: (1) the protobuf node protocol (single source, generate TS and Rust code from it), (2) the OpenAI wire format at the gateway edge, (3) the shared data store / internal API between control plane and gateway. Do not duplicate business rules in both languages: the control plane owns all writes to accounts, orgs, pools, keys, limits, enrollment and node registration; the gateway only reads that state (cached) and writes usage records. **Enrollment never touches the gateway**: nodes enroll against the control plane (Fastify/BFF) over HTTPS; the gateway only sees nodes that are already registered.
- **Gateway config cache (decided)**: the gateway keeps node records, pools, models, API key hashes and limits in its own process memory. **No Redis**; the live registry of connected nodes holds socket handles and is in-process by nature. Sync from the control plane's database:
  - The control plane writes a row to a `config_changes` table (seq, entity type, entity id, org id) in the same transaction as every config change. After commit it sends a Postgres `NOTIFY` (push, wake-up only; notifications may be lost) whose payload carries the new `seq`. A `seq` jump versus the gateway's cursor means a missed notification and triggers an immediate catch-up.
  - On startup the gateway does `LISTEN` first, then reads a consistent snapshot and its change `seq`, then catches up from that `seq`.
  - A single consumer task wakes on `NOTIFY`, on `LISTEN` reconnect (immediate catch-up), or on a 30s backstop poll, reads changes after its last `seq` with a small overlap window (sequence values can commit out of order), de-duplicates by entity, **re-fetches the current row** (never applies diffs; a missing row means delete), and swaps it into memory. Re-applying is idempotent.
  - If the gateway sees a gap, or was disconnected longer than the log retention, it does a full resync.
  - Applying a change has side effects on live state: a deleted, revoked, re-keyed or unapproved node has its socket closed immediately; a pool change moves its registry entry; a revoked API key rejects new requests at once.
  - If the database is unreachable the gateway keeps serving the last known config, exposes the feed lag as a metric, and may fail closed after a configurable maximum staleness (new inference requests get `503` with `Retry-After`, like the usage flush fail-closed rule; it recovers automatically once the feed catches up).
  - **API keys in memory**: the cache maps `hash(key)` to org, pool, limits and status. Keys are long random secrets with a readable prefix and a key id (for display and revocation), so a fast hash (SHA-256) is sufficient; compare in constant time. Only hashes are ever stored or cached, never the secret. A cache miss falls back to one database lookup (so a newly created key works immediately, before the change event arrives), with a short negative cache to blunt invalid-key floods. Revocation arrives through the change feed and takes effect for new requests at once.
  - Usage counters and rate-limit state are also in gateway memory, flushed to `usage_records` in batches (limits are approximate across instances within the flush interval).
  - Usage records are the only metering store: counters keyed by (minute bucket, org, pool, key id, model) with tokens in/out, requests and errors, flushed with an additive upsert (`ON CONFLICT DO UPDATE SET x = x + EXCLUDED.x`) so several instances add up. The gateway counts tokens itself; node-reported counts are never trusted for metering. **Prometheus and OpenTelemetry are deliberately deferred** (decided not to add them yet); if added later, never use API key or org as a metric label, and never put prompts or completions in spans.
  - **Usage flush failures and retries**: a failed flush never drops counters.
    - Each flush is one transaction. Unflushed counters stay in memory and are merged into the next batch; retry with exponential backoff and jitter, never blocking the request path.
    - Each batch carries a unique batch id recorded in the same transaction (e.g. a `usage_flushes` table with a unique constraint). If a commit outcome is ambiguous (connection dropped after COMMIT), the retry hits the constraint and becomes a no-op, so the additive upsert cannot double count.
    - The in-memory buffer is bounded and sized to ride out ordinary database failovers (tens of minutes of traffic; a minute bucket is a few hundred bytes). **Default policy (decided): fail closed.** The gateway returns `503` with `Retry-After` for new inference requests as soon as either the buffer is full or the oldest unflushed bucket is older than a configurable maximum age (default ~10 minutes, like the config feed's maximum staleness), so no unmetered traffic is served and nothing is lost. It recovers automatically once a flush succeeds. A deployment that prefers availability over exact billing (self-hosted, LAN) can switch to drop-oldest via config, which drops the oldest minute buckets and logs the loss.
    - Flush on graceful shutdown (SIGTERM). A hard crash loses at most one flush interval of counters, the same approximation accepted for limits.
    - Flush lag, failure count and buffered bucket count are logged now (never prompts, completions or key material), and become metrics if Prometheus is added later.
  - A shared store (Redis) or broker (NATS) is only considered for multi-gateway presence/forwarding, never for config or the live registry.
- The OpenAI handler and the node registry must stay in the same gateway process (see Architecture rules).
- **Control plane implementation (decided, `src/control-plane`)**: Fastify 5 + `fastify-type-provider-zod` (zod 4), PostgreSQL via **Drizzle ORM** (`drizzle-orm` + `pg`; schema in `src/db/schema.ts` is TypeScript but plain SQL migrations are generated by `drizzle-kit generate` into `drizzle/` and committed, so the Rust gateway can read the same tables with its own SQL; never hand-edit applied migrations). Entities so far: organisations, memberships (owner/admin/member), pools, `usage_records` + `usage_flushes` (metering store, **written by the gateway only**; `pool_id`/`key_id` have no foreign keys on purpose so history outlives deleted pools and keys; the control plane only reads them), `config_changes` (the gateway feed; `recordConfigChange` inside the transaction, `notifyConfigChange` after commit). DTOs are zod schemas in `src/dto` (**no shared package**: the UI copies the schemas it needs; keep them in sync by hand). Every route validates params/body/response with them and is documented in OpenAPI; **Swagger UI at `/api/docs`** (`/api/docs/json` for the spec); its Authorize button signs in through Dex (authorization code + PKCE with the public `splitcortex-ui` client, whose Dex `redirectURIs` therefore include `<web app origin>/api/docs/static/oauth2-redirect.html` in every environment; a pasted bearer token also works). All public routes live under the `/api` prefix (the ingress does not strip it); probes `/healthz` (liveness) and `/readyz` (DB) are at the root. Auth: `Authorization: Bearer <Dex token>` verified with `jose` against the Dex JWKS (issuer = `dex.config.issuer`, audience = `splitcortex-ui`; the JWKS URL defaults to the in-cluster Dex service so no public TLS is needed from the pod); there is **no users table** (Dex owns identities; the user is read from the token claims, `GET /api/me` echoes them) and memberships reference the lowercased token email as plain text. Tenant checks go through `requireOrgRole` (non-members get 404). The ingress serves `/api` on the **web app host** (same origin as the SPA, so no CORS). Validation messages in shared schemas are i18n keys.
- **Org/pool/member API (decided)**: organisations (get/update/delete; delete is owner-only and records a config change for each cascaded pool so the gateway drops them), members (list/add by email/change role/remove or leave) and pools (get/update/delete) are done, plus `GET /api/organisations/:orgId/usage` (any member; `from`/`to` capped at 92 days, `granularity` hour|day, optional `groupBy` pool|key|model and `poolId`/`model` filters). Role rules: owners manage everyone; admins only manage plain `member`s and cannot hand out a higher role; anyone may leave; the **last owner can never be demoted or removed** (owner rows are locked `FOR UPDATE` in the transaction). Route tests run against the real migrations on in-process Postgres (**PGlite**, `src/test/harness.ts`), no external database needed. Also done: pool settings (serving/balancing type), **nodes** (`nodes`: registered devices; list per pool, view, approve/rename, revoke; **no create endpoint yet, that is enrollment**) and **`node_status`** (live CPU/memory/battery/temperature/in-flight/tokens-per-sec, **written by the gateway only**; a node is online only while `connected` AND the row is under 60 s old, so a crashed gateway cannot leave nodes looking online; stale telemetry is not shown), and **models** (below). Deleting a pool or organisation records `node` changes for the cascaded nodes so the gateway closes their sockets. **API keys** (`api_keys`, `api_key_pools`; `routes/api-keys.ts`): admin/owner only, `GET/POST /organisations/:orgId/api-keys`, `DELETE .../:keyId` (soft revoke, idempotent). Token `sc_` + 32 random bytes base64url, shown once in the create response; only `sha256(token)` (hex) is stored plus a 10-character display prefix. Optional expiry (must be in the future), `created_by`, `last_used_at` (written by the gateway), `revoked_at`. Create, revoke, a deleted pool (cascades the scope link) and a deleted organisation all record an `api_key` change so the gateway drops or refreshes the key; the gateway checks `revoked_at`/`expires_at` itself. Still missing: enrollment, benchmarks.
- **Models and object storage (decided)**: models are organisation-scoped (`models`, `pool_models`; unique name per org; only `.litertlm`, max 32 GiB). Files live in an **S3-compatible bucket; Garage**, single node, the `garage` Helm subchart 2.5.0 from `https://charts.derwitt.dev` (a thin wrapper of upstream Garage; image overridden to the multi-arch `dxflrs/garage`, replication factor 1; credentials random in our `garage-credentials` Secret: `rpcSecret`, `token`, `access-key`, `secret-key`; the subchart installs a ClusterRole for its Kubernetes discovery CRD). **Garage is internal only: no ingress, no public S3 host, no CORS** (earlier design had browsers PUT to presigned URLs; replaced so storage is never exposed). The subchart bootstraps nothing, so a **Helm hook Job `garage-bootstrap` (post-install/post-upgrade, control plane image, `storage/bootstrap-cli.ts`) bootstraps Garage** through the admin API (`garage-admin:3903`, ClusterIP): layout for the node, ImportKey, bucket, AllowBucketKey; idempotent, retries while Garage settles, a plain Job under Tilt that the control plane depends on. Only that Job holds the admin token (API replicas never do, so replicas cannot race). Without S3 configuration the model endpoints answer 503. **Uploads pass through the control plane, streamed, never buffered**: `POST /models/uploads` returns `{model, partSize, partCount}` (8 MiB parts, grown for huge files to stay under 10,000), the browser `PUT`s each part as `application/octet-stream` to `/models/:id/parts/:n` (Content-Length must equal the expected part size; the request is piped into S3 `UploadPart`; returns the ETag), then `POST /models/:id/complete` verifies the stored size (mismatch deletes the object and fails the model). Parts are small because Traefik's default 60 s request read timeout applies to each (no entryPoint timeout changes). **Hugging Face URLs** are mirrored once by an in-process worker (`models/mirror.ts`, DB-claimed with `FOR UPDATE SKIP LOCKED`, stale claims recovered after 2 min, progress heartbeat that doubles as cancellation): only `https` on `huggingface.co`/`*.hf.co`, redirects followed manually and re-checked each hop (SSRF), the optional `HF_TOKEN` is sent to `huggingface.co` only, the file is hashed (sha256) while streaming and size-checked. Nodes never talk to Hugging Face; how nodes download from the platform (signed URLs over the gateway/node protocol) is not built yet. Abandoned multipart uploads are not yet cleaned up (add a sweeper).
- **Migrations**: `controlPlane.migrate` runs `dist/db/migrate.js` as a Helm hook Job (`post-install,pre-upgrade`, so the schema is updated before a new version rolls out and Postgres already exists on first install; the script retries while Postgres is down). Under Tilt it is a plain Job (`control-plane-migrate`) that `control-plane` depends on; the dev image runs it through `tsx`. New migration files are not live-synced, so Tilt rebuilds the image and re-creates the Job.
- Still open: a Cargo workspace for the gateway, PAKE library availability in Node (server side) and React Native (device side), see Security.

## Domain model

- **User**: registers an account.
- **Organisation**: created by users; has members with roles (membership management).
- **Pool**: an inference pool owned by an organisation; contains device nodes and serves a set of models.
- **Node / device**: a phone, RPi, etc. registered to a pool. Runs LiteRT-LM.
- **API key**: belongs to an organisation, scoped to the whole organisation or to chosen pools; used by clients to call the gateway.
- **Model**: owned by an organisation (a `.litertlm` file in object storage, added from a Hugging Face URL or uploaded), assigned to pools; every node of a pool holds all of the pool's models (serving type `replicated`).
- **Usage record**: token usage per key / pool / org, used for limits and dashboards.

## Architecture rules

- The platform has a **control plane** (Fastify: accounts, orgs, pools, keys, config, dashboards) and an **API gateway** (Rust: auth, limits, metering, load balancing, model management). They are separate services sharing a data store; the gateway never owns configuration data.
- Nodes connect **outbound** to the gateway over a persistent **WebSocket** connection secured with **TLS** (wss), carrying **protobuf** messages. Multiplexing is application-level: every message carries a request id, with credit-based backpressure, ping/pong keepalives and reconnect with resume. The protobuf schema is the versioned node protocol contract; keep it transport-independent. There is **no message broker** for now: the gateway keeps an in-memory registry of connected nodes per pool and relays requests and streamed tokens over the node's stream. Keep the node connection behind a transport interface (e.g. `NodeChannel`) so multi-gateway scaling (shared registry, gateway-to-gateway forwarding, or NATS) can be added later. Never design anything that requires inbound connectivity to a device.
- The gateway exposes the **OpenAI API format** (e.g. `/v1/chat/completions`, `/v1/models`, streaming via SSE) so existing OpenAI clients and SDKs work by changing only the base URL and API key. Keep this wire format at the gateway edge; translate to the internal node protocol behind it.
- The gateway has two distinct legs; do not conflate them. The OpenAI handler and the node registry/sockets must live in the same process (or instance group), so the client-facing endpoint must not be split out into a separate service or function:

  ```
  client ──HTTPS + SSE (OpenAI format)──▶ gateway ──WebSocket + protobuf (wss)──▶ node
          client-initiated, per request                node-initiated, long-lived, multiplexed
  ```

- The web app includes a **performance measurement** feature (e.g. benchmarking nodes and pools: latency, throughput, tokens/sec). Measurements must be scoped by organisation like all other data, and must not log prompts or completions (benchmark prompts excepted if they are platform-supplied).
- Every inference request must be authenticated by API key, checked against limits, routed to a healthy node in the target pool, and metered (tokens in/out).
- **Routing (gateway)**: API key hash, then org, limits and target pool, then a node from the in-memory live registry.
  - **An API key is scoped to the whole organisation or to a set of pools** (`api_keys.all_pools`, or rows in `api_key_pools`; an org-wide key also covers pools created later). The OpenAI format stays unchanged: clients only change base URL and key, and the gateway **resolves the pool from the request's `model`**: among the pools the key may use that have the model assigned and ready, pick one that has eligible nodes (if several do, balance across them by in-flight load); none serves it, `404` unknown model. `/v1/models` lists the union of the models of the key's pools. A key whose pools were all deleted matches nothing. Extra headers/paths to choose a pool are not used.
  - The live registry is keyed by `(org, pool)`. A node's org and pool come from its registered record (loaded from the database after proof of key possession), never from messages on the stream.
  - Eligible nodes are connected, healthy, have the requested model ready and have credits. Choose according to the pool's **balancing type** (`pools.balancing_type`, editable per pool): `weighted_p2c` (default: power-of-two-choices on in-flight requests, weighted by measured tokens/sec, since devices vary a lot), `least_in_flight`, `round_robin` or `random`. The pool's `serving_type` is `replicated` (the only value; sharding is future work behind the placement abstraction).
  - Failures: node drops before the first token, retry once on another node; drops mid-stream, end the stream with an error (no silent restart, to avoid double metering); no eligible node, `503` with `Retry-After`; limits exceeded, `429` before any node is touched.
  - The registry is per process. With several gateway instances a request must reach the instance holding the pool's nodes (single instance or sticky routing by pool for now); gateway-to-gateway forwarding is future work behind `NodeChannel`.
- Models are **replicated** per device for now. Keep model placement behind an abstraction so sharding a large model across devices (open research) can be added later without rewriting the gateway.
- **LiteRT-LM** is the only supported engine. Keep the engine behind an interface; do not leak LiteRT-LM specifics into gateway or billing code.
- Tenant isolation is critical: every query, node stream and registry entry must be scoped by organisation.

## Security

- API keys: store only hashes, show the secret once at creation.
- Node authentication must be per-device credentials, revocable individually.
- **Node identity**: each node generates its own public/private key pair on the device. The private key never leaves the device (use the platform secure keystore where possible). On enrollment the node registers its public key with the platform; the gateway authenticates the node by proof of possession of the matching private key (challenge-response signed during or right after the TLS handshake). Identity comes from the registered key, never from messages on the stream.
- **Server identity**: the server has its own key pair. Nodes learn and trust the server's public key (pin it at enrollment) so they can verify the gateway independently of the TLS CA chain.
- **Enrollment** (initiated from the web app, completed on the device):
  - An admin picks a pool in the web app, which creates an enrollment record (org, pool, expiry ~10 min, single-use, attempt-limited) and shows a **short code** formatted `XXXX-XXXXXX` (Crockford base32, no ambiguous characters). The same code is also shown as a QR for devices with a working camera; the QR is only a convenience and carries the enrollment (BFF) URL plus the same code. **Every device must be able to enroll by typing the code** (no camera required).
  - The first part (4 chars) is a lookup id, unique among all active enrollments across organisations (unique index; not reused until expired). The second part (6 chars) is the secret. Store only a verifier/hash of the secret server-side. The code reveals nothing about org or pool before success.
  - The mobile app takes the code and an **enrollment URL (the control plane / BFF), which has a default and is user-editable** (self-hosted or LAN deployments). The node talks to the BFF, never to the gateway, during enrollment; the PAKE rounds run over plain HTTPS request/response, with in-progress PAKE state kept in the database (or another shared store) so any BFF instance can serve any round.
  - Device keys are **never derived from the code**: the device generates its own non-exportable key pair in the secure keystore. The code only authorizes registering that public key.
  - Because the code is short, use a **password-authenticated key exchange (PAKE; CPace or SPAKE2)** keyed by the secret part, so the code authenticates both sides and cannot be attacked offline. Inside the PAKE-protected channel the BFF sends the **gateway's** public key and the gateway wss URL (the device pins the key) and the device sends its public key and device info. The BFF therefore needs to know the gateway's public key (from configuration or the shared store). This is what lets a short code replace a long pinned-key QR. A fake BFF at an edited URL learns nothing from the exchange.
  - Online guessing is bounded: a few attempts per enrollment, then it is invalidated, plus per-IP rate limits. The secret is single-use and consumed in the same transaction that registers the device.
  - Optional per-pool **admin approval**: the device appears as pending in the web app, showing a short fingerprint of its public key for the admin to compare, and is only active once approved.
  - After enrollment the code is dead; each connection authenticates with the signed challenge. Revoking a node means deleting its registered public key.
- Open decisions: PAKE choice and library availability on React Native/Expo (spike early; if no usable library, fall back to TLS with CA validation plus mandatory admin approval, and document the weaker first-contact trust), code length and TTL, whether approval is on by default, bulk code generation for many devices, key algorithm (Ed25519 is the likely default), server key rotation, and whether the key pair is used only for authentication or also to sign messages and model manifests.
- Validate TLS properly on the node connection; no disabled certificate checks, even in dev shortcuts. The node also verifies the gateway against the pinned server key.
- Do not log prompts, completions, or key material.

## Commands

- Helm chart: `helm lint chart --strict [-f chart/values-stg.yaml]` and `helm template` with the same flags. Local dev install (`--wait` is required so the ClusterIssuer hooks run after the cert-manager webhook is ready): `helm upgrade -i --wait --timeout 5m --create-namespace -n splitcortex -f chart/values-local.yaml splitcortex chart`.

- Tilt: `tilt up` at the repo root uses the root `Tiltfile` (k3s context `default`, Docker registry `localhost:5000` mirrored in k3s `registries.yaml`). It installs the infra chart as a `chart` local_resource via `helm upgrade -i --wait` (not tilt's `helm()`, because of the ClusterIssuer hooks) with the app workloads disabled (`--set ui.enabled=false --set controlPlane.enabled=false`). Each service has a `docker_build` plus `k8s_yaml(local('helm template ... --show-only templates/<svc>-*.yaml'))` so Tilt owns its workload and swaps in the built image; the `ui` and `control-plane` (plus its `control-plane-migrate` Job) services are wired up, the others are commented placeholders.

- CI/CD for images: reusable template `.github/workflows/docker-service.yaml` (`workflow_call`: `service`, `context`, `dockerfile`). It builds each architecture **natively in parallel** (linux/amd64 on `ubuntu-latest`, linux/arm64 on `ubuntu-24.04-arm`; no QEMU), pushes each image by digest to `ghcr.io/<owner>/splitcortex-<service>`, uploads the digests as artifacts, and a `merge` job creates the multi-arch manifest with the tags (`docker buildx imagetools create`). GHA cache scope is per service and platform. PRs build only (no login, push or merge). Tags: `vX.Y.Z` gives `X.Y.Z` and `X.Y` (no `v`, matches the chart `appVersion`), branch pushes and manual runs give `<branch>` and `sha-<short>`. Each service has a thin caller workflow (`ui.yaml`: PR, push to main with path filter, manual, and `workflow_call`; no tag trigger) and a new service adds one.
- Release: `.github/workflows/release.yaml` is the **only** tag (`v*`) entry point. It calls `chart.yaml` (validate, package, push OCI) and every service workflow in parallel, then `deploy.yaml` for `stg` once all succeed (add a job per new service and list it in `deploy-stg`'s `needs`). `chart.yaml` has `workflow_call` and no tag trigger. Chart version, `appVersion` and image tags are all `X.Y.Z`.
- Deploy: `.github/workflows/deploy.yaml` (`workflow_call` and `workflow_dispatch`, inputs `environment` stg/prd and `version`) checks out the tag, substitutes `LETSENCRYPT_EMAIL` into `values-<env>.yaml` and runs `helm upgrade -i --wait --atomic` from `oci://ghcr.io/<owner>/charts/splitcortex`. It runs in the GitHub environment of the same name, which holds the secrets `KUBECONFIG` (plain or base64) and `LETSENCRYPT_EMAIL`; add required reviewers to `prd` for a manual gate. Run it manually to redeploy or roll back; prd is manual only. The cluster must be reachable from GitHub-hosted runners, and GHCR packages must be public or the cluster needs an imagePullSecret (not wired in the chart yet).
- CI/CD for the chart: `.github/workflows/chart.yaml` lints (`--strict`), renders and kubeconform-validates the chart for each of dev/stg/prd on PRs and pushes to `main`. Pushing a tag `vX.Y.Z` packages the chart and pushes it to `oci://ghcr.io/<owner>/charts`. Chart dependencies (`~/.cache/helm`, `chart/charts`) and the kubeconform binary are cached with `actions/cache`, keyed on `Chart.yaml`/`Chart.lock`. Keep action versions on the latest major.

- Web UI (in `src/ui`): `pnpm install`, `pnpm dev` (Vite on :5173; open it as `http://app.splitcortex.127.0.0.1.nip.io:5173` so the Dex URL and redirect URI match the registered client), `pnpm build` (`tsc -b && vite build`), `pnpm typecheck`, `pnpm test` (Vitest run once) / `pnpm test:watch`, `pnpm format` (Prettier write) / `pnpm format:check`. Formatting is **Prettier**, configured in the repo-root `.prettierrc` (single quotes, semicolons, width 100, trailing commas) with `.prettierignore`, plus a root `.editorconfig` (UTF-8, LF, 2 spaces, final newline). Run `pnpm format` before committing UI changes.

- Control plane (in `src/control-plane`, own pnpm project and lockfile like the UI, Docker context `src/control-plane`): `pnpm install`, `pnpm dev` (tsx watch, needs `DATABASE_URL` and `OIDC_ISSUER`), `pnpm test`, `pnpm typecheck`, `pnpm build` (tsup), `pnpm db:generate` (new migration from schema changes, no DB needed), `pnpm db:migrate`, `pnpm format`. CI: `.github/workflows/control-plane.yaml` (listed in `release.yaml`).

- Node app (in `src/node`): `pnpm install`, `pnpm typecheck`, `pnpm test`, `pnpm format` / `pnpm format:check`, `pnpm exec expo export --platform android` (bundle check without a device), `pnpm exec expo prebuild` then `pnpm exec expo run:android` / `run:ios` (local dev build; no EAS, no Expo Go). Add Expo packages with `pnpm exec expo install <pkg>`.

CI for the node app: `.github/workflows/node.yaml` (PR/push with path filter, manual). Job `verify` runs typecheck, format check, Jest and an Android `expo export`; job `android` runs `expo prebuild` + `./gradlew assembleDebug` and uploads the debug APK as an artifact (14 days). No image, no deploy, `release.yaml` calls it on a tag (`node` job, no `push` tag trigger) and its `github-release` job attaches the APK, named `splitcortex-node-vX.Y.Z.apk`, to the GitHub release (created with generated notes if missing). On a tag it builds a **signed release APK** (`assembleRelease`): the keystore comes from the repository secrets `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` (create them with `src/node/scripts/create-keystore.sh [--upload]`; **back up the keystore, losing it means installed apps can never be updated; never commit it**), read through env vars by the local config plugin `plugins/withReleaseSigning.js` (without them a release build falls back to the debug key, e.g. locally). The version follows the tag: CI sets `APP_VERSION` (tag without `v`) and `app.config.ts` uses it as `version` and derives the Android `versionCode` (X*10000+Y*100+Z, so minor and patch must stay <= 99). Non-tag builds are debug APKs named after the commit. iOS is not built in CI (macOS runners and signing, later).

## Layout

- `chart/`: Helm chart, currently a **skeleton**: `Chart.yaml`, `templates/_helpers.tpl` (naming/label helpers) and empty `values.yaml` (local dev), `values-stg.yaml`, `values-prd.yaml` (overrides layered with `-f`), plus an optional git-ignored `values-local.yaml` for personal local overrides. It depends on the official **Traefik** chart (`traefik/traefik` 42.4.0 from https://traefik.github.io/charts, toggle with `traefik.enabled`, default on) and **cert-manager** (`jetstack/cert-manager` v1.21.3 from https://charts.jetstack.io, toggle with `cert-manager.enabled`, default on, CRDs enabled in `values.yaml`). **Dex** IdP (`dex/dex` 0.26.0 from https://charts.dexidp.io, toggle with `dex.enabled`; `image.tag: latest` with `pullPolicy: Always` (moving tag, not reproducible; pin a version tag if that matters); `enablePasswordDB: true`, `oauth2.skipApprovalScreen: true` (no grant-access screen), `expiry.idTokens: 15m` (Dex access tokens), refresh tokens 2160h (~3 months) for both `validIfNotUsedFor` and `absoluteLifetime`, Kubernetes storage; exposed through Traefik ingress at `https://dex.splitcortex.127.0.0.1.nip.io` (issuer URL; TLS from `root-ca-issuer`, `rate-limit-general` middleware, which assumes namespace `splitcortex`; stg/prd override this to `https://dex.stg.splitcortex.com` / `https://dex.prd.splitcortex.com` with the `letsencrypt` ClusterIssuer; each also registers the public `splitcortex-ui` static client and `allowedOrigins: ["*"]` plus an `allowedHeaders` list); the initial user `alinflorinciu@icloud.com` with a bcrypt hash is only in git-ignored `values-local.yaml`). **PostgreSQL** (`groundhog2k/postgres` 1.6.8 from https://groundhog2k.github.io/helm-charts/, toggle with `postgres.enabled`; service name `postgres`). `templates/postgres-credentials.yaml` generates the random superuser and app-user passwords once (reused on upgrade via `lookup`) into the fixed-name Secret `postgres-credentials` (kept on uninstall, matching the retained PVC), which also carries a ready `DATABASE_URL`; the subchart values only reference that Secret's keys, never passwords. `templates/cluster-issuers.yaml` defines ClusterIssuers as Helm post-install/post-upgrade hooks (CRDs and webhook come from the same release; install with `--wait`; not removed on uninstall): `root-ca-issuer` (CA issuer backed by a self-signed root, via a `selfsigned-issuer` bootstrap) everywhere, and `letsencrypt` (Let's Encrypt **production** ACME, HTTP-01 through Traefik) only in stg/prd, enabled by setting `letsencryptEmail` (the only issuer-related value; in `values-stg.yaml`/`values-prd.yaml` it is the placeholder `"${LETSENCRYPT_EMAIL}"`, substituted at deploy time with `envsubst '$LETSENCRYPT_EMAIL' < chart/values-<env>.yaml` from a CI variable, and the template fails if the placeholder is left in; CI validate substitutes a dummy address; names and settings are hardcoded in the template, do not add issuers to values); `Chart.lock` is committed and `chart/charts/` is git-ignored (run `helm dependency build chart`). Workloads, services, ingress and secrets will be re-added as the services land. Constraints for when they are:
  - Postgres is external; the gateway needs a direct connection (it uses `LISTEN`), not PgBouncer transaction mode.
  - Gateway default is 1 replica (registry is per process; more replicas need sticky routing by pool). The ingress controller is Traefik; SSE and wss must not be cut by Traefik's entryPoint `respondingTimeouts` (static Traefik config).
  - The gateway server private key comes from a Secret mounted as a file; only the public key and wss URL go to the control plane as plain config. Prefer `existingSecret` outside dev; no inline secrets in stg/prd.
  - External ingress / cert-manager are supported. External ingress controller: `traefik.enabled=false`, set `ingress.className` (also used by the ACME HTTP-01 solver) and `dex.ingress.className`, `rateLimit.enabled=false` unless it is Traefik with its CRDs, and replace the `traefik.ingress.kubernetes.io/*` annotations on the Ingresses. External cert-manager: `cert-manager.enabled=false` (CRDs and webhook must already exist; our `root-ca-issuer`/`letsencrypt` names must not clash). To use the external cert-manager's own issuers, also set `clusterIssuers.enabled=false` and point the Ingress `cert-manager.io/cluster-issuer` annotation at them.
  - Dev only, toggle `dev.coredns.enabled` (on in `values.yaml`, off in stg/prd): `templates/coredns-custom.yaml` creates the k3s `coredns-custom` ConfigMap in `kube-system` with `rewrite name exact <host> traefik.<ns>.svc.cluster.local` for each host in `dev.coredns.hosts` (currently `dex.splitcortex.127.0.0.1.nip.io`), so pods resolve the nip.io names to Traefik instead of 127.0.0.1. It replaces any existing `coredns-custom`; add new dev hostnames to the list.
  - HTTP to HTTPS: Traefik's `web` entryPoint redirects everything to `websecure` (`traefik.ports.web.http.redirections.entryPoint` in `values.yaml`; 302 in dev, 301 in stg/prd). This is global, so individual Ingresses need no redirect middleware. cert-manager HTTP-01 still works because Let's Encrypt follows redirects. With an external ingress controller, configure the redirect there.
  - The Traefik IngressClass is named `traefik` (`traefik.ingressClass.name` in `values.yaml`), independent of the release name; Ingresses and the ClusterIssuer's HTTP-01 solver use it.
  - Traefik rate limits: `templates/rate-limits.yaml` defines Middlewares `rate-limit-general` (per client IP, 50/s burst 100; web app, control plane, Dex) and `rate-limit-gateway` (per `Authorization` header, 2000/s burst 4000, a coarse flood ceiling only; the gateway enforces real per-key limits). Values under `rateLimit`. They are **not** on the entryPoint (that would throttle the gateway): attach per route via `router.middlewares` / IngressRoute. Nothing is attached until routes exist.
  - No Redis, no serverless. Enrollment goes through the control plane ingress, never the gateway.

- `src/ui/`: web app, containerised with `Dockerfile.dev` (Tilt: Vite dev server with live_update) and `Dockerfile` for production (multi-stage: pnpm test, then pnpm build, then Caddy on 8080 with SPA fallback, `/healthz`, non-root) and `Caddyfile`; chart templates `ui-deployment/ui-service/ui-ingress.yaml` under the `ui:` values (ingress on by default at the web app host). It is a Vite + React + TypeScript app; `src/` is split into `auth/` (OIDC provider, `PrivateRoute`, current user), `components/layout/` (sidebar (always visible on desktop; overlay drawer with a hamburger toggle on mobile), top bar, user menu with the theme and language submenus), `pages/`, `i18n/`, `theme/`, `lib/`; static assets and `locales/` in `public/`.

- `src/control-plane/`: Fastify API (`src/app.ts` builds the app from injected `db` and token verifier so tests need no infrastructure; `routes/`, `plugins/auth.ts`, `dto/` zod DTOs, `db/` with `schema.ts`, `migrate.ts`, `config-changes.ts`; `drizzle/` generated SQL migrations), `Dockerfile` (prod, runs tests, prod-only deps, non-root), `Dockerfile.dev` (Tilt, `tsx watch` on 8080). Chart templates `control-plane-{deployment,service,ingress,migrate-job}.yaml` under `controlPlane:` values (stg/prd override image and host).

## Working conventions

- **No resource requests or limits anywhere in the chart** (no `resources:` on our workloads or subcharts); do not add them.

- **Every new deployable project/service must ship with**: (1) a `Dockerfile` in its folder (build context = that folder unless it needs shared packages), run as non-root, with a health endpoint; (2) chart templates named `<svc>-deployment.yaml`, `<svc>-service.yaml`, `<svc>-ingress.yaml` (and others as needed) under a `<svc>:` values block with `enabled` (ingress enabled by default where it is public, per-env host/TLS/issuer overrides in `values-stg.yaml`/`values-prd.yaml`); (3) a Tiltfile entry (`docker_build`, `k8s_yaml` from `helm template --show-only`, `k8s_resource` with `resource_deps=['chart']`) and `--set <svc>.enabled=false` on the chart install; (4) CLAUDE.md and README updates for the above. The UI (`src/ui`) is the reference implementation.
- **Tilt uses a dev image.** Each service has `Dockerfile` (production) and `Dockerfile.dev` (used only by the Tiltfile `docker_build`): the dev one runs the service's hot-reload dev server/watcher on the same container port as production (so the chart's Service, Ingress and probes work unchanged, including a `/healthz` endpoint) and the Tiltfile adds `live_update` (sync sources, `fall_back_on` dependency manifests and config). Dev-only chart overrides (e.g. writable root filesystem) are passed with `--set` in the Tiltfile's `helm template`, never baked into `values.yaml` defaults. UI: `src/ui/Dockerfile.dev` runs Vite on 8080.
- **Image names differ per environment.** Local (Tilt) uses the bare name `splitcortex/<svc>` (the chart default; Tilt substitutes the locally built image). stg/prd override `<svc>.image.repository` in `values-stg.yaml`/`values-prd.yaml` to the GHCR path `ghcr.io/alinflorin/splitcortex-<svc>` (UI: `ghcr.io/alinflorin/splitcortex-ui`); the tag defaults to the chart `appVersion`. Keep the chart default and the `docker_build` name in the Tiltfile identical. CI builds and pushes service images to GHCR (see CI/CD above).

- **Always keep CLAUDE.md and README.md up to date.** Any change to a decision, architecture, security design, stack, commands or layout must update both files in the same change (CLAUDE.md for rules and constraints, README.md for the product-level overview). Do not leave them stale or contradicting each other or the code.
- Prefer small, focused commits. Do not commit unless asked.
- Open research items (multi-device model sharding) belong in the README roadmap, not as speculative code.
